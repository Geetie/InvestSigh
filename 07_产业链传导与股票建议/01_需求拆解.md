# 第七章《产业链传导与股票建议》逐节需求拆解

> 分析对象：`02_可编辑源稿_v2.md` 第七章（第 209–252 行）。沿用第九章、第六章已验证的六段式范式。
> 核心定位：**第七章是全系统的"结论生成层"**——它把第六章进来、第九章存下的证据与对象，转成"某公司受何影响、影响怎么传、现在该买还是卖、一条建议长什么样"。它的上承是第六/九章，下接第十章 T03/T05–T11。
> 三条贯穿主线：① **关系是"研究路径"而非"结论依据"**（每家公司独立判断）；② **传导的每一步都必须有依据、有符号、有停止条件**；③ **收益比较规则有前置门，且缺口宁缺毋滥**。
> **版本**：v1.1（2026-09-15 回改；**本文件回改明细见文末「附：回改记录」（唯一权威）**）

## 2. 深度挖掘专章

### 2.1 关于 7.1 关系建模

#### (a) 九类关系方向的统一表达

九类关系的"方向语义"分三种，无法用同一个"方向"字段表达：

| 关系类型 | 类别 | 方向语义 | 传导符号规则（已知 X 影响时 Y 的方向） |
|---|---|---|---|
| 供应采购 | flow | 有向：供应商→客户 | 需求信号逆产品流方向传播（客户需求↑→供应商营收↑，正号） |
| 制造封装 | flow | 有向：代工→委托方 | 同供应采购 |
| 产品采用 | flow | 有向：提供方→采用方 | 同供应采购 |
| 授权 | flow | 有向：授权方→被授权方 | 权利金反向流动；许可方收益≈被许可方销量 |
| 渠道 | flow | 有向：厂商→渠道→终端 | 同供应链，含加成/库存 |
| 投资关系 | flow | 有向：投资方→被投方 | 资本流正向；被投方经营↑→投资方权益↑ |
| 竞争替代 | correlation | 无向 | 反向耦合（**-1**）：X 利好≈Y 利空 |
| 互补 | correlation | 无向 | 同向耦合（**+1**）：X 与 Y 需求同向 |
| 合作验证 | joint | 无向（联合结果） | 联合成功条件成立时同号，否则不传导 |

**统一建模**：一条边 = `relation_class ∈ {flow, correlation, joint}` + `relation_type`（9 枚举）。flow 类带 `from_role/to_role` 与 `flow_kind`；correlation 类带 `coupling_sign ∈ {+1, -1}`；joint 类带 `success_condition`。**一个枚举（9 类）+ 一张方向规则表即可覆盖九类**——规则表把 9 类映射到 3 个 class，每个 class 一条符号规则。

#### (b) 产品流 / 资金流 / 需求信号分别表示

| 边 | `flow_kind` | 方向 | 关键字段 | 语义 |
|---|---|---|---|---|
| 产品流 | `product` | 供应商 → 客户 | `product_id`、`volume/value`、`stage` | 实物/服务的交付方向 |
| 资金流 | `capital` | 付款方 → 收款方 | `amount`、`currency`、`period` | 对价支付方向（与产品流相反） |
| 需求信号 | `demand_signal` | 需求方 → 供应方 | `intensity`（定性/定量）、`basis` | 需求变化方向的信号（与产品流相反） |

**为什么合并成一条关系边会出错**：
1. **方向不一致**：产品流出、资金流入、需求信号又反向——三方向无法压成一个。
2. **存在性解耦**：可以有"需求信号上升"但尚无订单，也可以有产品交付但资金未到账；合并会丢失"已知需求、未知订单"这类关键态。
3. **误把信号当收入**：需求↑ ≠ 收入↑（有库存/时滞/验收），合并会直接把需求信号折算为收入。
4. **去重需要分开**：同一终端需求可同时驱动多个供应商（N7.2-09），只有把需求信号独立成边才能做"根终端需求"归因与去重。
5. **证据/阶段不同**：订单阶段 vs 回款阶段的证据不同，合并无法分别记录。

#### (c) 订单 / 采购承诺 / 资本开支 / 排产 / 收入 语义层级

| 概念 | 语义 | 已发生 vs 计划 | 可否撤销 | 对应 N9.1-07 合作阶段 | 等同会导致的错误 |
|---|---|---|---|---|---|
| 收入 | 已确认（recognized） | 已发生 | 否 | `收入`（承第四/九章硬件阶梯） | ——（最"实"） |
| 排产 | 公司内部生产计划 | 计划（基于已知需求） | 可调整 | `排产` | 把内部计划当已出货/已收入 |
| 资本开支 | 需求侧投入（预算/在建） | 计划 + 部分已发生 | 可延后/削减 | 不作为供给侧阶段（属需求侧事件） | 把客户预算当对某供应商的确定订单 |
| 采购承诺 | 合同层面约束的承诺 | 计划（有约束力） | 一般不可撤 | `订单`（承诺级） | 把承诺当已确认收入 |
| 订单 | 客户意向/合同，可取消 | 计划 | 可取消 | `订单` | 把订单直接等同收入（跳过出货/验收/回款） |

**"实"的排序**（从最实到最虚）：收入 > 排产（已排产较实）> 资本开支（看是否已支出）> 采购承诺 > 订单。
**关键陷阱**：第四/九章要求硬件区分「订单→排产→出货→验收→收入→回款」——**任何"跳级等同"都必须被拦截**（如"订单=收入"会虚增营收；"资本开支=订单"会把客户预算当供应商订单）。

#### (d) 7.1 字段 vs 第九章 relations 字段核对（需新增字段）

第九章已有（N9.1-06/07/08/09）：关系键（主体,客体,产品,类型,有效期）、产品代际、合作阶段、有效期、经济暴露、证据。

| 需新增字段 | 归属 | 依据 |
|---|---|---|
| `relation_class` | relations | N7.1-02 |
| `coupling_sign`（-1/+1） | relations（correlation 类） | N7.1-02 |
| `relation_flows`（子表） | 新表 | N7.1-03 |
| `flow_kind`（product/capital/demand_signal） | relation_flows | N7.1-03 |
| `product_flow.{volume,stage}` | relation_flows | N7.1-03 |
| `capital_flow.{amount,currency,period}` | relation_flows | N7.1-03 |
| `demand_signal.{intensity,basis}` | relation_flows | N7.1-03 |
| `business`（业务对象） | 新对象 | N7.1-01 |
| `service`（服务抽象） | product 扩展或新对象 | N7.1-05 |
| `relation_progress_stage`（订单/承诺/排产/收入语义层） | relations 扩展 | N7.1-10 |

### 2.2 关于 7.2 传导（技术难点集中区）

#### (a) 停止条件（可执行、程序检查）

从节点 N 向下扩展一跳前，须通过以下全部检查，否则停止：

| # | 条件 | 判定 | 停止行为 |
|---|---|---|---|
| 1 | 依据门槛满足 | 目标类型对应的必需字段非空（见 (c)） | 不成立 → 标"依据不足" |
| 2 | 经济重要性 ≥ 阈值 | `economic_magnitude` 或`重要性`≥阈值 | 低于阈值且非"未知但重要" → 停 |
| 3 | 未访问过该节点/边 | 该对象不在本条路径中 | 已访问 → 记环、停 |
| 4 | 正向 > 反向力量 | 六要素中 |反向力量≥正向| → 标"方向存疑"或停 |
| 5 | 证据非纯重复 | 证据集 ⊄ 上游证据集 | 纯重复 → 不增权、停放大 |
| 6 | 终端需求未计数 | `terminal_demand_id` 未计 | 已计 → 不重复计入 |
| 7 | 累计放大幅度未超上限 | 累计 ≤ 上限 | 超限 → 收敛衰减 |

**程序检查而非模型自觉**：以上 1–7 全部落在**结构化字段**上（门槛字段、重要性数值、路径集合、符号、证据集合、terminal_demand_id、累计值）。模型只负责**抽取字段**（变量/方向/幅度/依据/证据引用），**程序负责判定与停止**（承 N9.2-03 精神）。这样停止条件可单测、可审计。

#### (b) 三种去重的可执行定义

1. **循环路径**：对本事件的传导边集建有向图，跑环检测（DFS / Tarjan SCC）。发现环 → 把环折叠为一个代表节点，冲击按**代表值（max，而非求和）**计入一次，记 `cycle_collapsed=true`，丢弃回边。**规则**：同一 (node, terminal_demand) 在一次传导中至多贡献一次。
2. **同一终端需求**：为每条路径段维护 `terminal_demand_id`（根需求）。归因时，**同一 `terminal_demand_id` 只计一次**；两个下游共享同一终端需求时，按**分摊比例**分配（不各自全额计入）。识别方法：不同中间环节沿依赖链回溯到同一 `root_demand_entity` 即判为同一终端需求。
3. **重复证据**：衔接第六章 `claim_propagation` 与 `independent_evidence_count`（N6.3-04）。若某跳的证据全部是已计证据的转述（同源）→ 不增证据权重；若该跳证据集 ⊂ 上游证据集 → 该跳**不带来独立证据**，不放大。

#### (c) 依据门槛形式化（可程序校验）

一跳有效的必需条件（按目标类型分级）：

```
base_required   = relation_id ∈ relations AND len(evidence.claim_id[]) >= 1
                  AND variable != null AND direction ∈ {+,-,0,unknown} AND condition != null

specific_entity = (target_type == 'specific_operating_entity')
                  ? require( location != null OR supply_mode != null OR procurement_link != null )
                  : true

hop_valid = base_required AND specific_entity
```

**证据不足时的输出**：**不丢弃、标"依据不足"保留**（N7.2-05）。具体：该跳标 `evidence_insufficient=true`，进入待核验线索队列（承 N6.4-05 gap 语义），展示为"推断路径（依据不足）"，**不生成受益结论、不进入建议依据集**。

#### (d) 云厂商资本开支 4 跳链路（方法论验收样例）

| 跳 | 传导 | 所需证据类型 | 依据门槛 | 变量/方向 | 反向力量 | 时滞 |
|---|---|---|---|---|---|---|
| ① | 云厂商 capex↑ → 服务器/GPU 供应商 | 云厂商 capex 指引/公告（一手）+ 供应关系（已核验） | capex 事件有一手来源 + 关系已核验 + 投入类别明确 | 采购额/份额（未披露=UNKNOWN），正号 | 采购向自研/替代供应商转移 | 1–2 季 |
| ② | 供应商 → 代工/封装 | 供应商产能/代工关系（已核验）+ 供应商订单/排产 | 代工关系已核验 + 供应商 stage ≥ 订单 | 排产/出货，正号 | 产能瓶颈、良率 | 1 季 |
| ③ | 代工 → 上游设备/材料 | 设备供应关系 + 代工厂 capex/扩产公告 | 关系已核验 + 扩产公告 | 设备订单，正号 | 扩产延后、制程切换 | 2–4 季 |
| ④ | 数据中心 → 电力公司 | **数据中心地点 + 供电方式/采购关系**（N7.2-05 硬门槛） | 目标为具体经营实体 → location/supply_mode/procurement_link 至少一项非空 | 购电需求，正号 | 自备电、电网调度、区域竞争 | 数季 |
| — | **反例** | 无地点/供电/采购依据 | **门槛不满足 → 该跳不成立** | —— | —— | 不能从 GPU 需求直接推所有能源公司受益 |

> ①②③ 为 flow 类（有向、正号）；④ 是"依据门槛"的关键验收点：**缺地点/供电方式/采购关系即判不成立**。

#### (e) 六要素 与 impacts 字段对齐

| 六要素 | impacts 字段 | 备注 |
|---|---|---|
| 影响变量 | `impacts.variable` | 结构化变量名 |
| 方向 | `impacts.direction ∈ {+,-,0,unknown}` | 不确定用 unknown，不硬给方向 |
| 幅度或范围 | `impacts.magnitude_type ∈ {quantified, range, qualitative, unknown}` + `magnitude_value/range/qualitative` | **未披露禁止点估计** |
| 成立条件 | `impacts.conditions[]` | 缺条件则该跳不成立 |
| 反向力量 | `impacts.counter_forces[]` | 与正向比较决定方向 |
| 体现时间 | `impacts.lag` / `horizon` | 支撑"为何现在形成为建议" |
| （承 N9.1-16）反证 | `impacts.counter_evidence[]` | 与第六章证据衔接 |

**"幅度或范围"未披露时**：用 `magnitude_type=qualitative`（强/中/弱/未知）或 `range {low, high}`；**禁止猜测点值**（承 N6.4-01 / N7.1-11）。

### 2.3 关于 7.3 建议规则

#### (a) 5 行规则 → "若…则…"与输入来源

| 规则 | 判定条件 | 输出 | 输入对象 |
|---|---|---|---|
| R1 买入 | 若 `研究完成 AND 可解释预测存在 AND 预期绝对收益>0 AND 预期个股收益 > 同期基准收益` | 可出买入建议（无最低超额门槛） | 研究基线状态、估值对象、收益预测(DerivedValue)、基准收益 |
| R2 卖出 | 若 `有依据预计无法继续跑赢基准` | 建议卖出（即便正收益） | 收益比较结果（相对） |
| R3 待判断 | 若 `暂时无法判断是否跑赢` | 待判断/复查中 + 缺口（≠卖出） | 缺口对象 |
| R4 维持 | 若 `新材料未改变投资判断` | 维持原判断 + 记录核查（不制造新信号） | 判断变化检测 |
| R5 强制复查 | 若 `单纯价格明显下跌` | 强制复查后重新判断（不自动止损/抄底） | 价格快照 + 触发阈值 |

#### (b) 前置门（N7.3-06/07）

- **"已完成相应研究"判定**：对应 N9.1-05 研究深度 = `研究基线完成`（或有可解释预测的更高态）+ N9.1-17 基线齐备。
- **"可解释预测"最小形式化**：必须同时具备 ①驱动假设集合 ②判断期限 ③收益（点估或区间）④底稿引用（指向 compute 层 DerivedValue + 假设版本）。缺任一 → **不可应用收益比较规则**。
- **"随意填数字"的程序拦截**：预测值必须可追溯到 compute 层 `DerivedValue`（含公式 + 操作数引用 + 假设版本，承 N9.2-02/03）；**无 DerivedValue 的收益值不可采纳 → 拒绝生成建议**。人工设定值必须显式标 `assumption_source=manual` 并留在假设层，不冒充测算结果。

#### (c) 边界情形"未约定"的表达

"预期绝对收益为负但仍可能跑赢基准"的**既有积极建议**处置未约定。系统表达方式：
- 标 `recommendation_status = boundary_unresolved`（显式"未决边界"），进复查队列；
- **不**自动转卖出、**不**新增买入；
- 待完整样例校准后再定义规则。
> 这样"缺省行为"= **挂起待决**，而非"卖出"或"维持"，从而**不引入隐含新规则**（N7.3-09）。

#### (d) "未改变"的判定与记录

- 判定：`judgment_change = (fact_set_changed OR assumption_changed OR conclusion_changed)`；全 false → `maintained`。
- 记录：生成一条 `check_record`（核查记录，非新建议、非新信号）；下游不产出新建议（避免每天生成无意义信号，N7.3-04）。

#### (b) "不编造实际持仓数量"防什么

结合第八章"卖出建议表示股票层面的退出判断，不代表系统知道用户实际持仓"。防的是：系统假设用户持仓、生成仓位相关建议（如"减仓 30%"）、把"卖出"当清仓指令、或据此推断用户盈亏；以及第二章"第一版不做个人组合仓位分配"。**约束**：recommendations 不含 quantity/position 字段；卖出=股票层面判断，与持仓无关。

#### (c) 催化剂：必填还是可空？"不存在" vs "未研究"

- **可空但须显式状态**：`catalyst_status ∈ {present, absent_confirmed, not_researched}`。
  - `present`：记录催化剂。
  - `absent_confirmed`：已研究并确认无催化剂 → 必须说明"价值可能被认识的路径 + 时间不确定性"（N7.4-10）。
  - `not_researched`：未研究 → 归入待判断/缺口（N7.3-03），不得冒充"确认无"。
- **对第八章每日研究页的影响**：`catalyst_status` 与 `review_date` 共同驱动"下一验证节点"展示；`not_researched` 显示为未完成研究，不产生新信号。

#### (d) 防止"关系传染"

- 原则：关系只能作**研究路径**（触发"对 B 做独立研究"），不能作**结论依据**（不能因 A 好就买 B）。
- 数据模型约束：relations/impacts **不直接写入** recommendations；recommendations 的每个结论必须引用**该标的自身**的研究基线（N9.1-17）+ 自身证据（claim_id[]）。
- 决策函数约束：不接受"关联公司的结论"作为输入，只接受"该公司的价值/价格/预测"。供应商与 NVIDIA 有关系 → 仅触发"对供应商独立研究"，不触发买入。

| 张力编号 | 涉及原文两方 | 冲突描述 | 裁决建议 |
|---|---|---|---|
| C7-1 | 7.2「不机械限制只能一层」 vs 「避免反复放大同一冲击」 | 深度自由 vs 成本与噪声控制 | 裁决：**深度由经济重要性动态决定，非固定层数**；同时用停止条件表（依据门槛/重要性阈值/环检测/重复证据/终端需求/累计上限）控制噪声。二者不矛盾——自由的是"按重要性决定深度"，受控的是"同一冲击不重复放大"。 |
| C7-2 | 7.3「不另设最低超额收益幅度」 vs 「不能随意填数字就出建议」 | 规则宽松 vs 前置门严谨 | 裁决：两者作用于**不同环节**。前者禁止在**收益比较环节**加额外门槛；后者设置在**前置门**（研究完成 + 可解释预测 + 可追溯 DerivedValue）。前者管"比较后的判定"，后者管"能不能进入比较"。 |
| C7-3 | 「待判断/复查中」 vs 「卖出」 | 第二章已定不能混同，但系统需明确行为 | 裁决：待判断=缺口态（不产出买卖），卖出=相对判断确定态。系统用**不同 status** 且**待判断不触发卖出动作**；展示层明确区分。 |
| C7-4 | 既有积极建议在"负收益但跑赢"下未约定 vs 系统需确定行为 | 缺省行为可能就是"隐含新规则" | 裁决：缺省=**挂起待决**（`boundary_unresolved` + 进复查队列），既非卖出也非维持；不新增买入。以此避免"缺省即新规则"。 |
| C7-5 | 「建议默认自动更新」（第八章） vs 第二章「不得悄悄增设买卖条件」 | 自动更新可能引入未经确认的条件 | 裁决：自动更新只更新**数据与既有规则**下的结论；规则集模型/系统均不得自增条件（承 N9.2-01）；任何新条件须经规则版本变更流程。 |
| C7-6 | 竞争替代（负向） vs 供应（正向） | 同一公司可能同时被正向与负向传导 | 裁决：**按跳分别取符号再聚合**（不用全局"同向"）；`coupling_sign` 与 flow 方向规则表分别定号；聚合时正负可抵消，禁止把网络标成同向（N7.2-03）。 |
| C7-7 | 「每家公司独立判断」 vs 传导本身意味联动 | 传导=联动，独立判断=不联动 | 裁决：传导产生**研究触发与影响变量**（路径），独立判断产生**结论**。关系只能作研究路径、不能作结论依据；recommendations 只引用该标的自身基线（N7.4-11）。 |

## 4. 最小可用数据集（按第十一章 5 阶段）

**阶段 1 需求与来源准备**
- `relations` 最小集：两端对象、类型、九类归类、合作阶段、有效期、证据引用、经济暴露（含 UNKNOWN）（**缺则首批关系核验清单无法产出**）
- `business` 对象 + 产品/服务抽象（**缺则"分别建模"不成立**）

**阶段 2 NVIDIA 深度样例**
- `impacts` 六要素 + 幅度表达规范（**缺则传导不可检查**）
- `recommendations` 8 字段 + 前置门字段（`calc_worksheet`/`derived_value`）（**缺则六步判断链不完整**）

**阶段 3 核心产业链运行**
- 产品流/资金流/需求信号三条边 + `coupling_sign`（**缺则多公司传导与符号判定失败**）
- 停止条件表 + 环检测/终端需求归因/重复证据去重（**缺则 T11 类去重与噪声控制失败**）
- 依据门槛规则（location/supply_mode/procurement_link）（**缺则 N7.2-05 无法验收**）

**阶段 4 每日持续研究**
- 判断变化检测 + `check_record`（**缺则每日噪声/无意义信号**）
- `catalyst_status`/`review_date`（**缺则每日研究页"下一验证节点"缺失**）
- `boundary_unresolved` 状态（**缺则边界情形变成隐含规则**）

**阶段 5 覆盖扩展与评估**
- `falsifiers`/`unmet_conditions`（**缺则三层复盘的预测质量不可核验**）
- 传导路径 as-of + 版本（**缺则历史回放不可行**）

## 6. 给架构师的交接要点

1. **关系边三分类 + 方向规则表**是传导正确性的地基：`relation_class ∈ {flow, correlation, joint}` + 9 类 `relation_type`，correlation 带 `coupling_sign`；禁止把整张图标成同向（N7.1-02/N7.2-03）。
2. **产品流/资金流/需求信号必须拆成三条边**（`relation_flows`），否则无法处理方向不一致、需求信号与订单解耦、终端需求去重（N7.1-03）。
3. **停止条件是可单测的程序判定**：依据门槛/重要性阈值/环检测(SCC)/重复证据/terminal_demand_id/累计放大上限——模型只抽字段，程序判定与停止（N7.2-01/08/09/10/11）。
4. **收益比较前置门 + DerivedValue 强制追溯**：无 compute 层 DerivedValue 的预测值不可采纳生成建议（N7.3-06/07）；这套门同时承载 T06/T07。
5. **边界情形用 `boundary_unresolved` 挂起**，缺省不等于卖出或维持，避免隐含新规则（N7.3-09）；"未改变"用 `check_record` 记录，不产新信号（N7.3-04）。
6. **关系只作研究路径、不作结论依据**：recommendations 只引用该标的自身基线+证据，决策函数不接受关联公司结论作输入，从数据模型层面杜绝"关系传染"（N7.4-11）。
