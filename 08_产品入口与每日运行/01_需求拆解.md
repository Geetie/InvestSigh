# 第八章《产品入口与每日运行》逐节需求拆解

> 分析对象：`02_可编辑源稿_v2.md` 第八章（第 254–286 行）。沿用已验证六段式范式。
> **章性质**：第八章是**产品入口层 + 运行调度层**——回答"**用户看到什么、每天系统自动做什么、失败时怎么办**"。
> **与第九章的分工（本文严守）**：**第九章定义对象与字段，第八章定义入口、流程、状态展示与调度**。故本文**只写"新增/需强化"的交互契约、调度契约、降级契约**，第九章已定义的 8 类对象、五类时间、版本不覆盖**只作引用、不重述**。
> **三条主线**：① **提问必须是真研究任务**（不是把问题存本地就完事）；② **事件状态与研究结论必须时间线可区分**（不能把"刚发现"包装成"已验证"）；③ **降级与幂等**（旧数据不标最新、重跑不重复产）。
> **本章需求统计**：39 条 = **P0 31 / P1 8 / P2 0**。（N8.1：9 条，P0 7 / P1 2；N8.2：8 条，P0 7 / P1 1；N8.3：12 条，P0 10 / P1 2；N8.4：10 条，P0 7 / P1 3。）

## 2. 深度挖掘专章

### 2.1 "提问必须是真研究"——最容易做成"假装研究"的地方

**为什么难**：聊天式问答（模型直接回答）看起来"用户得到了答案"，但**没有落成对象、没有证据、没有回写**——这正是原文 L268 要禁止的。判定"真研究"的三条硬标准：

| 标准 | 反例（假装研究） | 正确做法 | 验收 |
|---|---|---|---|
| ① **服务端任务** | 答案只存在会话/浏览器里 | 提问即建 `task`（`task_id`）落 `facts/tasks.jsonl` | 清空浏览器后任务仍在（T14） |
| ② **同流程** | 提问走"轻量问答"旁路，绕过证据门槛 | 走与自动监测相同 6 阶段 + 同 `evidence_gate` | 提问产出的结论与自动运行同字段/同门槛 |
| ③ **可追溯回写** | 回答像"通顺的话"就结束 | 回答带 **答案 + 证据（claim_id[]）+ 产生的更新（对象引用）** | 三件齐全，更新可回溯 |

**上下文继承（N8.2-02）**：继承"对象 + 页面 + 基线版本"三者，缺"基线版本"就无法解释"这个回答是基于哪一版研究"。

**与 T14 对齐**：T14 判据 = 提问实际产生研究任务 + 来源回答 + 可追溯回写，且失败状态可见。

### 2.2 "不能把未研究的事件包装成已验证结论"——靠四条时间戳与渐进式发布

**问题**：事件一进来就想"给结论"，会把"刚发现"渲染成"已确认"。原文 L276 要求：**四个时间戳分别记录 + 先显示发现/复查中，完成后再更新判断**。

| 时间戳 | 语义 | 承载 |
|---|---|---|
| 事件发现时间 | 系统首次发现该事件 | 事件对象 `first_seen_at`（复用 Ch9 时间字段组） |
| 入队时间 | 进入研究队列的时刻 | `enqueued_at`（新增，挂任务） |
| 研究完成时间 | 分析完成的时刻 | `analyzed_at`（复用 Ch9） |
| 发布结果时间 | 结果对外发布的时刻 | `result_published_at`（新增；**不叫 `published_at`**，因 Ch9 `published_at` 已是"来源公开时间"，见 §4） |

**渐进式状态机（展示层）**：

```
发现事件(discovered) → 正在复查(rechecking) → 判断更新(judgment_updated) → 结果发布(result_published)
```

- 前三态之间，页面**只能显示"发现/复查中"**；**判断未更新前不得显示新结论**（N8.3-07/08）。
- 与 Ch6 五态机的分工：Ch6 管**主张**的状态（`supported/disputed/...`）；本章管**事件→结论的发布时序**。二者不冲突，是"证据状态"与"发布时序"两层。
- **与"待判断"的措辞区分**：`待判断`=已研究但不足以定论（Ch7 R3）；`未研究`=事件已发现尚未分析。**两者都不得渲染为"中性/无机会/已验证"**（承 Ch3 N3.2-05、Ch2 P-10）。

### 2.3 "失败降级不得把旧数据标为最新"——三级状态不可合并

**原文 L284 三句红线**：保留上次有效结果 + 显示日期与失效状态；不覆盖为无意义空值；不把旧数据标为最新。

| 层 | 状态 | 字段 | 展示 |
|---|---|---|---|
| 采集/解析层 | 未完成解析 | `obtainable_content_type=no_transcript`/`headline_only` + `task_type=parse` | "尚未完成解析" |
| 主张层 | 未完成核验 | `claim.status=pending_verification` + `task_type=verify` | "待核验" |
| 数据可用层 | 失效/延迟 | `stale=true` + `stale_since`；`delay_flag` + `as_of_time` | "数据失效（截至 X 日）"/"延迟行情" |

> **承 Ch6 §G.2 的"两级状态"并扩为三级**：`未解析`（采集层）≠ `未核验`（主张层）≠ `未研究`（事件层）。**合并任意两者都会造成"虚假完成"**（如把"待核验"显示为"无结论"）。
> **与 Ch9 的接口**：`stale` 标记 + `last_valid_result_ref` 已由 Ch9 §3.4.8/§3.6 定义，本章只负责**展示与不变量**（不得置 null、不得改时间戳）。

### 2.4 "重复执行不得重复生成"——幂等键是本章的承重设计

**三类幂等键**（全部复用/对齐 Ch9 §3.6，本章不新建机制）：

| 产出 | 幂等键 | 命中行为 |
|---|---|---|
| 事件 | `event_fingerprint`（承 Ch9 §3.4.7，基于根来源） | 同事件重跑 → 不新建事件 |
| 建议 | `(security_id, issued_at, version)`（承 Ch9 §3.3.4） | 重复执行 → 命中即跳过 |
| 任务 | `task_idempotency_key` = `(gap_id 或 claim_id) + task_type`（承 Ch1 §C.3） | 同缺口重跑 → 不重复建单 |

**反例**：日报重跑一次 → 事件数翻倍、建议数翻倍 → 触发 T12 误判与"虚假变化"。**验收**：同日同输入重跑 N 次，`events`/`recommendations` 行数不变。

### 2.5 "通知/聚合不得改变投资规则"——排序是处理顺序，不是门槛

**原文 L262 红线**：通知渠道与聚合方式另定，但**不得通过通知过滤偷偷改变投资规则**。
**承 Ch2 P-09/P-10 与 Ch6 §B.2**：这与"排序 ≠ 门槛"（C123-4）是同一纪律：

| 允许 | 禁止 |
|---|---|
| 通知**处理顺序**用 Ch6 `priority_order` 字典序（tier→importance→time） | 用 `weight`/`score` 做"通知优先级打分"（P-09） |
| 聚合方式可配（渠道/时间窗） | 聚合**过滤掉**与投资规则冲突的内容（= 隐性改规则） |
| 每日页"重要信息"按字典序排 | "买入置顶/紧迫色"（P-10） |

**不变量测试**：同一批建议，在"通知开/关、聚合 A/B"下**结论集合与内容完全一致**（仅推送方式变）。这是本章最容易被"产品优化"悄悄破坏的地方。

### 2.6 增量重算与"追加式不可变"如何协调（承接跨章张力）

**问题**：L282 要"只重算受影响对象"，Ch4/Ch9 要"追加式不可变 + 双时间轴"——重算会不会变成"覆盖"？

**裁决口径**：**重算产出"新版本"，永远不覆盖旧版本**。

| 动作 | 做法 |
|---|---|
| 受影响对象重算 | 追加**新版本行**（`prev_version_id` 指向旧版） |
| 未受影响对象 | **不产生**新版本（Ch4 §H.2：无新信息不写） |
| 旧版本 | 保留，可 as-of 回看（Ch9 §3.4.1） |
| 依赖传播 | 走 `dependency_edges`（Ch9 §3.4.3）求受影响面 |

> 即 L282 的"只重算"是**范围**约束（省算力），不是**覆盖**授权；二者正交，不冲突。
