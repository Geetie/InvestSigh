## B. 赚钱机制的结构化对象 ★

### B.1 落位取舍：新建 `facts/businesses.jsonl`（业务单元，mechanism 内嵌）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 挂 `baselines` 下 | 少一张表 | baseline 是**版本化研究结论**（随研究更新换代），business 是**公司结构信息**（相对稳定，状态对象）；混在一起会让"业务定义"随研究版本爆炸 | ✗ |
| 新建 `facts/businesses.jsonl` | 业务/机制独立演进；baseline 只 `business_refs` 引用；对齐 N7.1-01"公司/业务/产品分别建模" | 多一张表 | **✓ 推荐** |
| 再拆 `revenue_models.jsonl` | 更细 | mechanism 与 business **1:1**，拆表只增 join 无收益 | ✗ |

**`business` schema**（`facts/businesses.jsonl`，状态对象 + `change_log`）：

```yaml
business_id: BIZ-NVDA-DC          # 主键
company_id: company_nvda
business_type: hardware           # model_class：见 C
metric_set_id: MS-HW-6STAGE       # 路由到指标集（C）
mechanism:
  payer: {party, segment, geographies}
  offering: [product_id|service_id...]
  revenue_model: one_time|subscription|usage|license|hybrid
  conversion_chain:                # 转换链路（分段，每段挂证据）
    - {stage, input, output, evidence: [claim_id...]}
  cost_structure: {main_cogs[], fixed[], ...}
  capital_requirements: {capex, rnd, working_capital}
```

**转化链路分段模型**（通用四段，按商业模式实例化）：**获取 → 交付 → 使用 → 变现**。
- 硬件：订单→排产/出货→验收→收入/回款
- 云：签约→通电/上线→利用率→收费
- 软件：使用→付费→续约/留存→增购

每段必有 `evidence`（`claim_id[]`，接第六章），否则该段标"待补证"（`segment.pending_evidence=true`）。

### B.2 每段证据要求

每段 `evidence` 为该段**该业务**的主张引用；`evidence` 空 → 标 `pending_evidence`，展示为"待补证"，**不阻止**业务建模但**阻止**该段进入财务连接（C）。

## C. 多业务多指标集路由 ★

### C.1 可配置的指标集定义（`rules/metric-sets.yaml`）

```yaml
- metric_set_id: MS-HW-6STAGE
  model_class: hardware
  currency: n/a
  stages: [order, production_schedule, shipment, acceptance, revenue, collection]
  metrics: [{name, unit, source_class, linked_account}]
  linked_accounts: [revenue, cogs, capex, inventory, receivables, ...]
- metric_set_id: MS-CLOUD-5STAGE
  model_class: cloud
  stages: [contract, energized, online, utilization, billing]
  ...
- metric_set_id: MS-SW-5STAGE
  model_class: software
  stages: [usage, paid, renewal, retention, upsell]
  ...
```

- `businesses.metric_set_id` 绑定；`business.model_class` 为路由键。
- **`business_id → indicator_set` 绑定**：指标**挂在 `business_id`（非 `company_id`）**。

### C.2 "混合公司防指标串味"的程序约束

```python
# scripts/valuelayer/route_guard.py
def validate_binding(business, metric_set):
    if business.model_class != metric_set.model_class:          # ← 外键一致性
        raise MetricSetMismatch(business.business_id, metric_set.metric_set_id)
    # 分部财务独立：指标只能写本业务分部科目，禁止跨业务引用
    for m in metric_set.metrics: assert m.owner_business_id == business.business_id
```

- **可测断言**：给混合公司（如 MSFT = cloud + software）的两业务各绑指标集，断言 `metric.owner_business_id` 与业务一致；跨业务引用被 `MetricSetMismatch` 拒绝。
- **汇总规则**：分部财务**在分部层完成后合并**，禁止跨业务直接引用指标（`scripts/valuelayer/rollup.py` 只做分部→公司层加总，不做跨业务语义混用）。

### C.3 三类是否穷举 → 扩展机制

| 动作 | 改哪个文件 | 要不要改代码 |
|---|---|---|
| 新增第 4 类（广告/代工/游戏内购…） | **只改 `rules/metric-sets.yaml`**（注册新 `metric_set` + 路由） | **否**（注册表驱动） |
| 未注册类型 | 归入 `MS-GENERIC` 并显式标注 `unregistered_model_class=true` | 否 |

### C.4 指标 → 财务科目 → 每股指标的**三层映射**（"财务连接"的实现）

落 `facts/drivers.jsonl` 的 `financial_link`：

```
driver.financial_link = {
  accounts: [revenue_segment, gross_margin, opex, capex, working_capital, ...],
  per_share_metric: eps | fcf_per_share | value_per_share,
  formula_ref: <DerivedValue ref>        # 走 scripts/compute/
}
```
例：`GPU 出货量 → 数据中心分部收入 → 每股收入`；`→ 毛利率/费用 → 净利润 → EPS`；`→ capex/营运资金 → FCF → 每股 FCF/每股价值`。**跨节引用一致性**由 G 的形式校验器检查（驱动必须出现在财务连接里）。

## D. 增长驱动与"增长的代价" ★

### D.1 驱动对象 schema（`facts/drivers.jsonl`）

```yaml
driver_id: DRV-NVDA-DC-01
business_id: BIZ-NVDA-DC
source_class: demand_expansion|share|price|product_mix|unit_usage|penetration|new_business|mixed  # 7 类 + mixed 兜底
duration: {mode: point|range, value: "1-3Y"}          # 可持续时长
financial_link: {...}                                  # C.4 三层映射
cost_of_growth:                                        # 五项代价（D.3）
  price_discount: {...} / capex_requirement: {...} / inventory_buildup: {...}
  receivables_buildup: {...} / financing_need: {...}
realization_stage: occurred|planned_guidance_forecast|conditional   # E（仅用于 driver 驱动三态；relations 侧用 relation_progress_stage）
timeline: {...}; confidence: {...}                     # E
importance_class: high|medium|low
```

### D.2 "少量关键驱动"上限、超限处理、可持续时长

| 问题 | 设计 |
|---|---|
| 上限 | `rules/baseline.yaml: max_primary_drivers_per_business`（默认 5，可配） |
| 超限处理 | 校验器**拒绝直接入库**；须先分级：`primary_drivers(≤5)` + `secondary_watchlist`（或按 `importance_class` 取 top-N，其余归档） |
| 可持续时长 | `duration.mode ∈ {point, range}`；未披露用 `mode=range` + 定性标注（**不给伪精确点值**） |

```python
def validate_driver_count(business, drivers, cfg):
    primary = [d for d in drivers if d.tier == "primary"]
    if len(primary) > cfg.max_primary_drivers_per_business:
        raise TooManyDrivers(len(primary), cfg.max_primary_drivers_per_business)
```

### D.3 五项"增长的代价" → 财务科目映射 + 增长质量

| 代价 | 财务科目 | 字段 |
|---|---|---|
| 降价 | 收入（单价↓）/毛利率 | `price_discount` |
| 增加资本开支 | 现金流量表投资活动 / CapEx | `capex_requirement` |
| 库存 | 资产负债表存货 | `inventory_buildup` |
| 应收 | 资产负债表应收账款 | `receivables_buildup` |
| 融资 | 筹资活动 / 净负债 | `financing_need` |

**增长质量 = 分档（不压成单一分数）**：`growth_quality ∈ {high, medium, low}`，由四项分项判定——`ROIIC vs WACC`、`现金转化率`、`营运资金变动`、`融资依赖`。

**"收入高增长但毁灭股东价值"如何被识别（对齐 N4.1-14）**：

```python
# scripts/valuelayer/growth_quality.py
def assess(driver, fin):
    roiic = compute_roiic(fin.incremental_nopat, fin.incremental_invested_capital)  # 走 compute/
    if roiic < fin.wacc:
        return GrowthQuality("low", flag="value_destructive_growth")
    ...  # 现金转化率/营运资金/融资依赖分项
```
> 机制：靠**大幅降价 + 大额 capex + 应收膨胀**驱动高增长的公司，若 `ROIIC < WACC`，每多投 1 元创造低于资金成本的回报 → `growth_quality=low` + `value_destructive_growth=true`。**收入增速不得作投资回报代理**（N4.1-14）：决策/估值只引用 `ROIC/ROIIC/每股 FCF/EVA`（`scripts/valuelayer/growth_quality.py` 输出的替代指标集），**收入增速字段设有 denylist 守卫**。

### D.4 【v1.1 回改 R-09】环境层承载（融资条件 → 增长代价）

> 环境层五类项**仅作输入**（第三章 N3.3-01/02），第四章承载"融资条件"一项：

| 环境项 | 第四章承载 | 字段 |

## E. 增长确定性的二维记录 ★

### E.1 兑现时间 × 判断置信度（两个独立字段，禁止合并）

| 字段 | 取值域 |
|---|---|
| `timeline`（兑现时间） | 具体日期/期间，或分档 `{≤1Q, 1–4Q, 1–3Y, >3Y}` |
| `confidence`（判断置信度） | `{high, medium, low}`（**不默认给数值概率**，承第五章） |

**四象限处理**（"很快但很不确定" vs "很久但很确定"在系统行为上不同）：

| | 高置信 | 低置信 |
|---|---|---|
| **近兑现** | 近期催化剂，重点跟踪 | **进高频验证队列**（标待核验），不重度依赖 |
| **远兑现** | **作长周期估值基础**（调长期限） | 仅作敏感性/情景，权重极低或不进基准预测 |

- 反例：驱动 A"6 个月内推出"（低置信）→ 高频验证 + 情景；驱动 B"3 年后确定" → 低频跟踪 + 长周期估值基础。**合并成"高中低"会丢失该区分**（N4.2-03）。

### E.2 驱动三态与 `relations.stage`、`claim_nature` 的对齐

| 概念 | 对象/字段 | 语义 |
|---|---|---|
| 驱动三态（已发生/计划指引预测/依赖条件） | `driver.realization_stage` | 该**驱动**处于哪一兑现阶段 |
| 合作阶段 | `relations.stage`（N9.1-07） | 该**关系**处于哪一合作阶段 |
| 主张性质 | `claim_nature`（第六章） | 该**主张**是事实/计划/预测/解释 |

**是三个视角，不是同一枚举**：驱动三态**由支撑它的 `claim_nature` 推导**，并以 `relations.stage` 佐证；同一驱动可含多条不同 nature 的主张，**取"最实"的支持证据**定 stage（`scripts/valuelayer/stage_derive.py`）。

## F. 护城河的落地 ★

### F.1 六种保护对象（多选）

```yaml
moat:
  - moat_id: MOAT-NVDA-01
    mechanism: "..."                       # 优势机制说明（必填）
    protected_objects:                     # ⊆ 六类，多选
      - {object: share|pricing|cost|customer_retention|capital_return|innovation_efficiency,
         strength: high|medium|low, evidence: [claim_id...]}
    origin_class: durable_advantage|product_cycle|supply_demand_cycle|operational_efficiency
    cross_generation_survival: true|false|unknown
    evidence_claims: [claim_id...]
```

### F.2 反误判规则的程序化

```python
# scripts/valuelayer/moat_guard.py
MOAT_EVIDENCE_KINDS = {"persistent_share","pricing_power","cost_advantage",
                       "switching_cost","scale_effect","network_effect"}

def is_durable_moat(moat, claims) -> bool:
    single_point = (moat.only_from({"product_leadership"})
                    or moat.only_from({"supply_scarcity"})
                    or moat.only_from({"high_gross_margin"}))
    if single_point:
        return False                                       # N4.3-06：单点证据不足以认定
    kinds = evidence_kinds(moat, claims) & MOAT_EVIDENCE_KINDS
    return (moat.mechanism_explained
            and len(kinds) >= 2                            # 需证据组合（≥2 类）
            and moat.cross_generation_survival is True
            and moat.origin_class != "supply_demand_cycle")  # 非周期性
```

**四者区分的判据字段**（看优势是否随周期/代际/供给变化而消失）：

| 类别 | `origin_class` | 判据 |
|---|---|---|
| 持续竞争优势 | `durable_advantage` | 跨周期、跨代际仍保持 |
| 产品周期 | `product_cycle` | 单代领先，下一代可能丢失（`cross_generation_survival=false`） |
| 供需周期 | `supply_demand_cycle` | 紧缺时高毛利，供给恢复即消失 |
| 经营效率改善 | `operational_efficiency` | 成本下降来自管理/规模，未必可持续 |

### F.3 护城河与价格数据的**硬隔离**（可直接写单测）

| 断言 | 内容 |
|---|---|
| A1 | `MoatInput` dataclass **不含**任何 price/return 字段：`assert not any(k in MoatInput.__dataclass_fields__ for k in {"price","return","snapshot","quote","past_performance"})` |
| A2 | 护城河字段写入源白名单不含行情：validator 拒绝 `moat.evidence_claims` 中引用 `price_snapshot_id` 的条目，抛 `MoatPriceContamination` |
| A3 | 价格变化只触发 `recheck`（`tasks`），**不能写入** `baselines.moat`：写路径断言 `moat.writer ∈ {research_skill, human}`，不含 `price_ingest` |

### G.2 "不是六个空标题"的可程序校验（反形式主义）

| 可自动校验（形式完备性） | 只能人工判断（实质质量） |
|---|---|
| 六项 section 非空且达最小字段数 | 推理是否成立 |
| 必填字段非空率 ≥ 阈值 | 假设是否合理 |
| ≥1 原始材料定位（locator） | 机制解释是否有洞察 |
| ≥1 推导（公式 + 操作数） | 竞争分析深度 |
| 跨节引用一致（驱动出现在财务连接里） | 结论可信度 |

```python
# scripts/valuelayer/completeness.py
def form_complete(baseline, cfg) -> CheckResult:
    checks = [sections_nonempty(baseline, cfg), 
              nonnull_rate(baseline) >= cfg.min_nonnull_rate,
              has_locator(baseline) >= 1,          # 含原始材料定位（N9.1-11）
              has_derivation(baseline) >= 1,       # 含推导（N9.2-02）
              cross_section_consistent(baseline)]
    return CheckResult(passed=all(checks), failed=[...])   # 形式上拦截空标题
```
> **最低标准**：程序做**形式完备性检查**（拦截空标题/无定位/无推导/跨节不一致）；**实质质量评审**只能人工（记 `tasks` 的 `human_review` 记录）。

## H. 3×4 状态与增量更新

### H.1 三个独立状态字段

```yaml
value_state:
  growth_momentum_state: strengthening|weakening|unchanged|tbd
  certainty_state:       strengthening|weakening|unchanged|tbd
  moat_state:            strengthening|weakening|unchanged|tbd                # 趋势（既有）
  moat_level:            weak|moderate|strong|tbd                            # 水平（v1.1 回改 R-05，新增）
```
- **三个独立字段**（禁止单一总状态）：第二章明确"动力增强、确定性减弱、护城河不变"可**同时出现**；三者是不同问题（增长空间 / 兑现把握 / 竞争壁垒）。
- **状态变更触发**：仅当**有 `claim_impact` 改变该维度证据**时。
- **"待判断" vs "不变"**：待判断 = **信息不足、无法判断**；不变 = **已研究且确认无变化**（两者语义不同，N4.5-03）。

### H.2 "没有新增信息时不制造状态变化"的程序化保证

```python
# scripts/valuelayer/state_machine.py
def update_states(old_states, new_info, impacts):
    if not new_info or not affects_dimension(impacts):
        return old_states, CheckRecord("本次核查无变化")   # ← 不写新版本
    return apply_changes(old_states, impacts), ...
```
> 状态变更函数**仅在 `new_info != ∅ AND affects_dimension` 时运行**；否则保持原值 + 记录核查（承 N4.5-05 / 第七章 `check_record`）。

### H.3 增量更新记录结构（复用 N9.1-33，不新建机制）

`baseline` 新版本追加行：

```json
{"company_id":"company_nvda","version":8,"prev_version_id":7,
 "increment":{"old_judgment":"...","new_info":["CLM-x"],"new_judgment":"...",
              "affected_period":"FY2027Q1","supporting_evidence":["CLM-x"],

 "value_state":{...},"changed_by":"research_skill",

```
- 直接复用第九章追加式不可变 + 双时间轴；旧版本可 as-of 回看（N4.5-01）。
