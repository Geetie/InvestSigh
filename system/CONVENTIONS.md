## 一、验证规范（V 系列）★ 最高优先级

### V-01 禁止「一条命令全量验证」

**规范**：**不得**用一条命令跑完整个测试套件 + 全部门禁 + 阶段判据。
必须**分批**，每批一个独立子进程。

**为什么**（实测故障）：旧版 `verify.py` 把 `pytest tests`（全量）+ 20 项门禁 + 阶段判据
塞进**一条命令、一个超时**。任一处卡住 ⇒ **整条命令零输出、退出码只剩 `137`（SIGTERM）**，
既看不出卡在哪一批，也拿不到任何证据。**定位成本远高于分批的执行成本。**

**强制手段**：`scripts/checks/verification_policy_guard.py` 断言
① `verify.py` 不带 `--batch` 时必须 **exit 2**（拒绝隐式全量）；
② **不存在**任何 pytest 批次以裸 `tests` 为目标的"全量批次"。

**正确用法**：
```bash
python system/scripts/ops/verify.py --list                      # 看批次与超时
python system/scripts/ops/verify.py --batch <名>                # 一次一批（推荐）
python system/scripts/ops/verify.py --batch all                 # 逐批跑，超时即停
```

### V-02 每批必须设定**适合的**超时时间

**规范**：每个批次必须带独立的超时上限，取值要让**偶发抖动不误报**、而"真的卡住"能**快速暴露**。

> ★ **倍数的适用边界（批次 10 审计 `G8` 修正）**：原措辞是"取实测典型耗时的 **8~30 倍**"。
>   实测**该经验值在慢批次上已不成立** —— 例如 `daily` 典型 43s，8× = **344s > 300s 上限**；
>   `guards`(18.5s) 按原值也只有 3.2×。
>   **根因**：那个倍数来自"批次都在 0.3~4s"的时代。当单批从 4s 涨到 43s，绝对余量已经够大
>   （180s 足以区分"慢"与"卡死"），再乘 8 只会撞上限。
>   → **现行判据**：**超时 ≤ 300s**，且**余量要能区分"慢"与"卡死"**（慢批次 4~8× 即可）。
>   `verification_policy_guard` 只强制 `0 < timeout ≤ 300s` —— 这是**刻意的**：倍数靠人判断，
>   把它做成硬门槛会逼出"为了过门禁而虚报实测值"。
>
> ★★ **标定超时必须在「工作树内」测，不得用隔离副本的秒数**（`ws-verify-shard` 实测的通用陷阱）：
>   本仓的部分耗散**只在工作树内出现** —— 同一个 273 项夹具副本，
>   **工作区内 `rmtree` 4.521s vs 工作区外（`/tmp`）0.046s（98×，≈16ms/项）**，
>   而 `copytree` 两边一样快。⇒ **隔离副本会把最贵的那一项测成 0**。
>   踩到的实例：`tests/injection/` 的 `f` 片隔离副本 **12.53s**、工作树内 **110.13s**（8.8×）；
>   若按隔离 ×8 取 **120s**，余量只剩 **1.09×** ⇒「天天误报的门禁一定会被关掉」（`G-01`）。
>   ⇒ 标定前先问一句：**这个耗时是在被测环境里测的吗？**

**为什么**：超时值就是**故障探测器**。设得过宽（如统一 600s），卡死就退化成"跑得慢"，
又回到 V-01 的老问题。

**强制手段**：守卫断言每批 `timeout > 0` 且 `<= 300s`，且 `BATCHES` 与 `ORDER` 键集合一致。

### ★ `tests/injection/` 为什么要**切成多片**（不是设计选择，是宿主配额决定的）

**根因（实测）**：夹具是**每个用例复制一份 `system/`**（`conftest.py::code_root`，
实测每份 **273 项**：`copytree(ignore=_ignore)` + `_ENSURE_DIRS` + `_make_writable` +
`_reset_truth_source` 之后 `os.walk` 计目录 + 文件）。宿主对**单轮（turn）**的删除操作有
**累积配额**（触发时报 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`，`scope: "turn"`；
守卫以「本轮的 `count`」对「`threshold`」比较）。`tests/injection` 全目录合并跑一轮的例数
（**现算值见 `verify.py` / `test_shard_coverage.py`，此处不写死**；原文写"165 例"**已过期**），
每例约 **792 计数**（实测 ≈ **2.9 ×** 夹具项数，见 §下面那条 ★★）≈ **13 万计数/轮**，
**远超阈值** ⇒ 越过阈值后**连单个用例目录都被拒删**，之后所有夹具 setup
直接报 `E` —— **症状看起来完全像"测试坏了"，实际是配额**。
⇒ 即 **`injection` 这个批次事实上等于被关掉了**。而本文件的铁律是
「**卡死的门禁 = 被关掉的门禁**」，故必须修，不能靠"知道就好"。
（`verify.py` 里原来那个以 `tests/injection` 为目标的**目录全量批次已删除** ——
 保留它就等于保留那个超配额的入口。）
★ **`threshold` 不是常量**：本单两次观测到 **`9999` 与 `99999` 两个值**
（当前宿主环境变量 `CODEBUDDY_SAFE_DELETE_BULK_THRESHOLD=99999`）。
故下面任何"安全片数"的结论都必须**带阈值的限定语**。

**代价（如实写明）**：完整覆盖 `tests/injection` 需要**与片数相同的轮次数**（每轮跑一片）。
这是**宿主删除配额决定的**，不是设计选择 —— 合并成一轮就必然重现上面那个"被关掉"的故障。
`--batch all` 会把各片连着跑完 ⇒ **恰好**会重新越过配额，在某一处突然变红。
**要完整覆盖该目录，请按片轮流次跑**（片数真源 = `verify.py::INJECTION_SHARDS`）。

★ **`--batch all` 这条禁令没有机器绑定，且不可能有**（`verify.py::INJECTION_SHARDS` 处也有同样一段注释）：
`--batch all` 的越界是**跨进程累积**的 —— 每一片单跑都是绿的，红的是**第 N 片之后的那一片**，
而那个进程无法知道自己前面已经删了多少。要在进程内拦它，就得让 `verify.py` 自己维护
"本轮已跑过哪些片"的跨进程状态，那是把一个**本可以用一句话说清的纪律**做成一套状态机
（过度设计，且状态本身会漂移）。**故此处用显式禁令 + 段落说明承担**，不假装有守卫。
⇒ 机器绑定管的是**静态可分片性**（穷尽/不重/不超量/目标形态，4 条断言）；
**"一轮一片"是使用纪律**（`V-08`）。两者分工不同，不要互相冒充。

**三条做法约束（都不可放宽）**：

1. **不许靠"缩小夹具副本"省配额**：明确**禁止**把 `scripts/` 或 `tests/` 从
   `conftest._COPY_SKIP` / 副本里去掉 —— 有些守卫**就是扫副本**的
   （`conflict_scan` 的 L2 扫 `code_root/scripts/**`；`verification_policy_guard` 扫
   `code_root/tests/**`）。去掉会让它们**扫到 0 个文件而"通过"**，
   那是比配额严重得多的**守卫静默失效**；
   → 已登记：原 `test_guards_reject.py` **单文件 41 例**（按 ≈792 计数/例 ≈ **3.2 万计数**，
   **本身就远超阈值**），故按 `# ═══` 分节边界**纯移动**拆成 `test_guards_reject_a.py`（21 例）+
   `test_guards_reject_b.py`（20 例）；两半共用的工具提到 `tests/injection/_guard_common.py`
   （**唯一真源**，`G-06`：不许两处各抄一份）。
2. **不许用 `-k` / 名字关键词分片**（`R-06 ①`：关键词式判据不可穷尽，
   **新用例会静默落进 `not` 分支**，而"漏测"与"测过没问题"在报告里长得一样）；
3. 片目标一律**显式文件路径**（目录式目标会一次拉起整个目录的用例 ⇒ 配额问题原样复发）。

**机器绑定**：`tests/injection/test_shard_coverage.py` 断言
① 各片目标文件的并集 **恰好等于** `tests/injection/` 下的测试文件集合（穷尽，不重不漏）；
② 各片目标**两两不相交**（重复收录 = 删除量翻倍）；③ 每片**用例数 `--collect-only` 现算 ≤ 32**
（该上限是**授权上限 + 只在观测到的较高阈值下成立**，见下面 ★★，不是推导常数）；
④ 片目标必须是**显式测试文件路径**（不是目录、不用 `-k`）。
片 ↔ 目录的**唯一真源**是 `verify.py::INJECTION_SHARDS`（判据现读它，**不靠批次名前缀猜**
 —— 那也是关键词式判据）。
★ 四条断言**各自都有反向对照**（`G-05`：每条拦截判据必须有反例，且必须是**真的会红**）：
漏文件 / 重复收录 / 超量 / 目标写成目录 —— 逐条反例与"删掉反例后转绿"的实测见
`reports/ws_verify_shard_report.md §2.3`（另有独立复现 §8.5）。

★★ **`32` 是"授权上限"，不是由 `9999 ÷ 273` 算出来的安全线** ——
  后者**已被实测证伪**（细节见 `reports/ws_verify_shard_report.md §8.1/§8.3`）：
  ① 宿主 `threshold` **两次观测不同**（一次 `9999`、一次 `99999`）；
  ② `count` 的**计数单位不是"夹具项数"**（实测 ≈ **2.9 × 项数/例** ⇒ 约 **792 计数/例**）。
  ⇒ 按 `9999 ÷ 792`，安全上限只剩 **≈12 例/片**，完整覆盖需 **≈14 片**。
  ★★ **故当前的分片（每片 ≤32）只标注为「实测可跑的当前配置」，不是「已证明安全」**：
  它成立的**前提是阈值处于观测到的较高值（`99999`）**。**若阈值回落到 `9999`，当前分片立刻不成立**
  （安全上限 ≈12 例/片 ⇒ 需 ≈14 片），必须重排 —— 重排是**主理人决策**（轮次数会随之抬高），已上报，未擅自改。
  ★ **片数与各片例数一律不在此处写死**（`#91`）：真源 = `verify.py::INJECTION_SHARDS` +
  `test_shard_coverage.py` 的 `--collect-only` **现算**断言。原文此处曾写「6 片 / 171 例」并逐片列 4 个例数
  —— 实测已全部漂移（片数 6→**7**；`a` 27→**30**、`b` 28→**32**、`d` 31→**29**、`f` 31→**27**，`g` 整行缺失）。
  上述口径**逐字写在代码里**：`test_shard_coverage.py::MAX_CASES_PER_SHARD` 上方注释 + 该断言的
  失败消息里都带"授权上限 / 阈值前提 / 回落时改成 ≈12 例"三句，避免下一个人把它当推导常数。

★★ **配额之外的第二重成本：工作区内的删除被宿主逐项监察**（实测 ≈ **16ms/项**）——
  同一份 273 项夹具副本：工作区内 `rmtree` **4.521s**、工作区外（`/tmp`）**0.046s**（**98×**）；
  而 `copytree` 两边一样快（0.106s / 0.102s）。
  ⇒ ① 全目录合并跑**光删除就要十几分钟**（按现算例数 × 每例 ≈0.75s，原文以"165 例 ≈12 分钟"计，
  该例数**已过期**）⇒ **既不可行也不被允许**；
  ② **标定超时必须在工作树内测，不得用隔离副本的秒数** —— 拿隔离副本的秒数标定会**必然假红**
  （实例：`injection-f` 工作树 **110.13s**、隔离副本 **12.53s** ⇒ 按隔离 ×8 得 120s，余量仅 **1.09×**）。
  故 `tests/injection/` 的各片统一取 **300s**（`V-02` 上限；对工作树实测 = **2.2~4.7×**）——
  与 `daily`（43s → 180s = 4.2×）同属"慢批次取不超过上限的最大值"，倍数的适用边界同 `V-02` 注。
  ★ 余量最薄的是 `injection-d`（136.80s / 300s = **2.2×**）与 `injection-f`（2.7×）；
  **见到这两片超时的第一步不是改断言，而是先确认有没有第二个 pytest 会话在同一工作树里跑**（`V-05`）。

★★ **配额触顶后的现象与边界**（2026-09-16 实测；★ 原文断言"**本轮内不恢复**"，**该措辞已被后续实测收窄**）：
  一旦命中 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`，**当时**此后连**单个**用例目录的删除都被拒
  （`targetCount: 1`），**任何建夹具的用例都跑不了**；隔数分钟重试，`count` **一个数字都没变**。
  ★★ **但"不恢复"不能推广成"本会话剩余时间必然红"**：同一天稍后、**同一会话、零 env 覆盖**下
  把 `verify.py` 的 **23 个批次全跑了一遍**，**全部 `exit=0`、一次告警都没有**
  （含 `guards`／`pricelayer`／`injection-b..d` 这些夹具重的批次；见
  `reports/ws_fixture_cost_report.md §6.6`）。⇒ **守卫"开"≠"一定收费"**，触发与否**依赖会话/阈值状态**，
  机制**尚未钉死**（旁证：报文自述 `"scope":"turn"`）。**不要**拿本条去预判"之后一定红"。
  ⇒ **可操作判据**：报"未测 / 环境红"之前，**先看输出里有没有那行 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`**
  —— 有 ⇒ 环境（该格未测，`G-60`）；**无 ⇒ 红/慢就是判据自己的事，不许归因环境**。
  ⇒ 至于"多片全红"看起来**极像"分片方案坏了"** —— 所以 `verify.py::_exit_zero` 里那条

### V-03 **超时 = 该批有问题**，且**绝不算通过**

**规范**：批次超时必须判定为**不合格**，并按下列优先级归因：

1. **极大概率是测试本身的问题**（死循环 / 竞态 / 环境依赖 / 资源累积）；
2. 其次是被测代码卡住；
3. **不是**"跑得慢"，不得以"延长超时"了事 —— 延长前必须先找出卡点。

**强制手段**：守卫断言超时码 `124` 经批次判定函数后**必然返回不合格**（含"超时"字样），
**不存在**把 `124` 当放行的路径。

**排查方法**（分批 + 二分 + 抓栈，实测有效）：

### V-04 验证必须**在沙箱外**跑（Python 层 broker 必须关）

**规范**：跑测试/门禁必须关闭 Python 层的 FS broker hook。

**为什么**（实测故障）：WorkBuddy 的 `sitecustomize.py` shim 把**每一次文件操作**
brokered 到宿主进程走 IPC：

```python
_IN_SANDBOX               = os.environ.get("CODEBUDDY_SAFE_DELETE_SANDBOX") == "1"
_BROKERED_FS_HOOK_ENABLED = os.environ.get("CODEBUDDY_BROKERED_FS_HOOK_ENABLED") == "1" or _IN_SANDBOX
```

**Bash 工具的沙箱开关关不掉它**（它在解释器层）。后果：测试夹具每用例 `copytree`
复制 130 个文件 ⇒ 每用例数百次 IPC ⇒ 数百用例累积**数万次**往返 ⇒
**broker 阻塞、进程卡死且卡点漂移**（实测卡在第 15/17/19 条不等，`exit 137`、零输出）。

**实测对照**：broker **开 → 卡死**；broker **关 → 12 次 copytree 每次 0.026s，12/12 全过**。

**强制手段**：守卫断言 `run_pytest.sh` 与 `verify.py` **都**把两个环境变量置 `0`；
`conftest.py::pytest_sessionstart` 在检测到 broker 启用时打印响亮警告。

**正确用法**：
```bash
sh system/scripts/ops/run_pytest.sh tests/<子目录>     # 直接跑 pytest 的唯一正确入口
python system/scripts/ops/verify.py --batch <名>       # 已内置同一环境修正
```

### V-05 验证**严格串行**，且必须**留档**

**规范**：不得并行跑两个 pytest；每批输出必须落盘。

**为什么**：`tests/conftest.py::pytest_sessionstart` 会整目录清理 `tests/.work/` ——
并行会话会**互删夹具**，产生不可复现的偶发失败。

**强制手段**：**人工 + 机器**（2026-09-16 起，见缺口 `G-RC-10`）。

- **人工（第一道）**：动测前先 `ps` 确认**同一工作树**内没有第二个 pytest 会话。
- **机器（第二道）**：`tests/conftest.py::pytest_sessionstart` 在 `tests/.work/.session.lock`
  取**排他会话锁**（记持有者 pid）。已被**活着的**会话持有 ⇒ `pytest.exit(..., returncode=4)`，
  **响亮失败**并给出可行动处置（等它结束 / 换一个 worktree），**不再静默地把对方的夹具删掉**。
  陈旧锁（持有者进程已死）**自愈接管**，不会永久锁死工作树。
  覆盖用例：`tests/guards/test_session_lock.py`（5 条，含"拒绝活着的并发会话""陈旧锁接管"
  "释放不误删他人锁""同进程重复取锁幂等"）。

> ★ **本条原先写的是"⚠️ 人工（守卫无法可靠检测并发进程）"，与实现相反** ——
> `G-RC-10` 落地后**代码强于文档**。按纪律 5（声明与实现必须机器绑定）已同步更正。
> ★ **残余（如实登记，不得当成"已完全防住"）**：
> ① 锁**只对"取锁之后启动"的会话生效**——先启动的旧会话（其 `conftest` 已载入旧版本）不会取锁；
> ② 锁保护的是**同一工作树**；**跨 worktree 本就不冲突**（各有自己的 `system/tests/.work`），
> 不需要也不应该串行；
> ③ 它**不能**阻止"人为故意绕过"（删锁文件再跑）—— 那是纪律问题，不是守卫能覆盖的。

**留档约定**：`verify.py` 自动写 `reports/verify_<批次>_latest.log`（每批保留最近 3 份）。
**引用证据一律读该文件，不必重跑。**

### V-08 **同一轮内只跑一次全量验证**（宿主删除配额，`V-03` 的姊妹条）

**现象**（实测多次复发）：同一轮里反复跑 `verify.py --batch all`，到第 N 次时某批会在 **1~40s 内提前红**，
日志尾部只有一行：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":86613,"threshold":9999,"scope":"turn","targets":[...]}
```

**这不是测试坏了**：单独 `run_pytest.sh tests/injection` 同一份代码是 **130 passed**。

**根因**：宿主对**每一轮**的删除操作有**累积配额**（阈值 `9999`，`scope: "turn"`）。
判据是"本轮累计删除的**项数**"，**不是**"单个目录的大小"——
实测同一目录 `find` 只有 251 项，而宿主计数 86k+。
而夹具是**每个用例复制一份 `system/`（约 250 项）用完即删**：一次全量 ≈ 119 用例 × 250 ≈ **3 万项**
→ **一次全量就可能逼近/耗尽配额**，之后**连删单个用例目录都被拒**。

**处置（按优先级）**：

1. **一轮内只跑一次全量**；诊断与迭代用**单批**（`--batch <name>`）或**单文件**（`run_pytest.sh tests/<dir>/<file>`）。
   ★ **`tests/injection` 现在切成多片**（片名与归属见 `V-02`，真源 = `verify.py::INJECTION_SHARDS`）：**每轮只跑一片**。
   那是这条配额规则的直接产物 —— 该目录**全量**跑一轮必然越过阈值（例数与每例项数见 `verify.py` 的现算值与
   `reports/ws_fixture_cost_report.md §2.6`）。
2. 需要反复迭代时：**新开一轮**（配额按轮重置）。
3. **不要**把"批次提前红"当成测试问题去改断言 —— 先看日志有没有 `SAFE_DELETE_BULK_CONFIRM_REQUIRED`。
4. 手工清理夹具目录时**分片删**（逐子项），不要一次 `rm -rf` 整个 `tests/.work`。

**为什么写进规范**：这个坑**看起来完全像测试失败**（退出码 1、有 E 标记），
实测已害我在同一轮里连续误判两次（先怀疑 `_reset_truth_source` 太慢，又怀疑夹具模板膨胀）。
**把它固化下来，比每次重新怀疑一遍便宜得多。**

### V-07 **新建工作树后、以及每次 `git merge` 之后，第一步必须跑 `bootstrap_worktree.sh`**

```sh
sh system/scripts/ops/bootstrap_worktree.sh
```

**为什么**（系统性伪影，不是谁的代码错）：纪律 9 要求 `rules/` 全 `0444`，但
**git 只跟踪可执行位、不跟踪只读位** → 任何 `git worktree add` / 新 clone / **`git merge`**
出来的 `rules/*.yaml` 都是 `0644` → `rules_lock_guard` **必红**（实测：`fix/claim-propagation`
与 `fix/compute-silent-defects` 两个工作树首次提交各被拦下 10 条）。

★ **`git merge` 也在触发面内**（批次 13 补，缺口 `G-53`）：`ws-ch2-rules` 在 `git merge main` 后
实测 `ls -l rules/*.yaml` = `-rw-r--r--`（644）—— 合并会按索引重写这些文件，**只读位同样丢失**。
`rules_lock_guard.py` 有 `st_mode & 0o777 == 0o444` 的显式检查 ⇒ 它**会红（不是静默失效）**，
但症状是"**每次合并都白红一次**"，且合并与下一次门禁之间存在一个**可写窗口**（窗口内的写入仍会被
SHA256 抓到，故仍是"检测得到"，非"静默"）。
⇒ 一律在 `git merge` 之后立刻跑本脚本；**不要**在各人自己的 `chmod` 上打补丁，更**不是**用 `--no-verify` 绕过。

★★ **触发面比"新建工作树 + `git merge`"更宽（批次 13 追加，`ws-ch2-rules` 实测）**：
**任何把该文件纳入索引的 git 操作**都会把它翻回 `0644` —— 实测**一条 `git add system/rules/<某件>.yaml` 就足够**。
⇒ 触发面应读作：`worktree add` / `clone` / **`git add`** / **`git commit`** / `checkout` / `merge`。
⇒ **稳妥做法**：**提交前**先跑一次本脚本（它只改权限位、`git status` 恒为空、不污染提交）；
**提交后**再用 `rules_lock_guard` 核一次。

★★ **并且`pre-commit` 不是经验上的沙箱**（同一个实测来源）：它**可被 `--no-verify` 绕过** ⇒
**不能作为纪律 9 的唯一强制点**。本项目对这一点已有结构性冗余：
`rules_lock_guard.py` **同时**在 `scripts/ops/run_all_gates.py` 的 `GATES`（24 项/25 条）里 ---- 
⇒ 即使有人绕过钩子，**全量门禁仍会拦**。**新增纪律 9 相关守卫时，必须同时进 `pre-commit` 与 `run_all_gates`（`G-07`）。**

**天天误报的门禁一定会被关掉**（`G-01`）→ 必须在流程层根治，而不是让每个工程师各自 `chmod`，
更**不是**用 `--no-verify` 绕过。

**边界**：该脚本**只改权限位** —— 不碰内容、**不碰 `registry/rules.lock.json`**
（用 `lock_rules.py` 代替会重写该被跟踪清单的 `locked_at` 与 SHA 台账 → 产生与任务无关的提交噪音）。
因此它的效果在 `git status` / `git diff` 上**恒为空**，不污染任何提交。

**强制手段**：`scripts/ops/bootstrap_worktree.sh`（自带 `rules_lock_guard` 自检，失败即 `exit 1`）。

## 五、判据评审规范（`G-62`「静默等价态」）

> **本节是「人工评审清单」，不是机器门禁** —— 按主理人裁定**不新增门禁**（新门禁是 `G-07` 的事）。
> 所以它的**强制手段只有两条**：① `§九 换人审计` 时**逐条问**并留痕；② 写新判据的人在提交前**自问一遍**。
> ★ 若某条被判"命中"，正确处置是**换载体 / 改判据 / 显式记账**，
> **不是**再加一条同类判据 —— 见 `R-06③`：不可穷尽者不得作为防护。

### 5.1 术语定义

**「静默等价态」** = 一种**异常状态**，其特征是它的**可观测结果**与"正常 / 成功 / 无事发生"**逐字相同**。

形式化：存在实质不同的两类情形 `A`（异常）与 `B`（正常），判据 `f` 满足 `f(A) == f(B)`（**输出同形**），
且**不存在第三个可观测通道**能把两者分开 ⇒ `f` 对 `A` 的**判别力为零**，却报"通过"。

★ **与"漏报"的区别（这决定了处置方式，别混）**：
- **漏报** = 该拦的没拦，但判据**本来能分辨**，只是没覆盖到那种写法 ⇒ 可以在 `R-06` 允许范围内**加强判据**；
- **静默等价态** = **输出通道本身不分辨** ⇒ **再加同类判据无效**，必须**换载体**
  （引入能分辨的观测：显式 note、独立计数、真源派生、可区分记账），或**让异常态响亮失败**。

★ **与 `G-01` 的关系**：`G-01` 管"命中**报不报**"（禁 warn-only）；`G-62` 管"命中**看不看得见**"。
**两件事，`G-01` 不能替代 `G-62`** —— 一个永远 `exit 0` 的守卫完全符合 `G-01` 的退出码契约。

### 5.2 评审必问项（Q1–Q8，每条给"命中"的可判定条件）

| # | 必问 | 判"命中"的条件 |
|---|---|---|
| **Q1 反事实** | 把被检对象换成**最坏的那一份**，判据输出**是否必然不同**？ | 输出**逐字相同**，或只差措辞/时间戳/路径 ⇒ **命中** |
| **Q2 空集** | 被检集合为**空**时走哪条分支？与"非空且全合格"的输出是否**同形**？ | 同形（既没有显式空样本 `note`，也没有单独计数）⇒ **命中**（`G-03`） |

| **Q7 可区分记账** | 判据"不通过"的原因有多个时，是否**分别记账**（不同 `note` / 不同计数）？ | 只有一条 `note` 或一个布尔 ⇒ **命中**（`G-RC-12`：「pathspec 指错」与「真没改」在 `git diff` 输出上**一模一样**） |

**Q2–Q5、Q7、Q8 是七类已知成因的定位器** —— 答"命中"时请同时给出**该成因**，

### V-09 **删除预算是「宿主 `rid`（回合）级**的资源 —— 跑批前必须披露本轮用量**

> ★ 标题于 **2026-09-16 更正**：原为「宿主回合级 + **全流共享**」⇒ "全流共享"**过宽**，
> 按实测改为「**同一 `rid` 内共享**」（见下「作用域」一节）。★ **旧措辞在此留痕**（`口径 10`：不静默改写）。

**为什么**（系统性约束，不是谁的代码错，见缺口 `G-59`）：宿主的 safe-delete 代理对**单轮删除次数**设上限
（实测阈值 `99999`，`scope: "turn"`）。而本项目的夹具会 `copytree` 每一份 `system/`
⇒ **单个测试文件的批量 `setup` 就能累积上万次删除**。一旦越限：

```

INTERNALERROR> … in _exit_bulk_guard_control → SystemExit: 1
```
其后**连单文件跑都立刻 `INTERNALERROR`**（此后每次夹具都继续累积）。

★★ **作用域：按 `rid`（回合）独立 —— 表述已更正，但执行纪律保持保守（2026-09-16 裁定 ①）**

- **实测**（`state.json` 直读，零删除）：`requests` 表里 **20 个 `rid` 各有独立的 `count`**

  ★★ **同源佐证**：守卫**自己的输出字段**就是 `scope: "turn"` ⇒ 与实测**同义**。
  ★ 另有两条必须一起读的边界：`threshold` **不是常数**（观测到 `9999` 与 `99999` 两个值）；
  「触顶后本轮不恢复」**已被证伪**（同命令相隔 1 秒：一次被拒、一次全绿）。
- ⇒ **表述**改为：「**同一 `rid`（回合）内不得有别的夹具流**」——
  **不是**"同一宿主"，也**不是** session 级"全流共享"。
- ★★ **但执行上仍按「同一宿主独占」**，四条理由：
  1. 实测只证了「**计数**各自独立」，**没证「配额**各自独立」—— 两者不是一回事；
  2. `state.json` 目录是**共用**的（同一份文件里同时住着多条流的记录）；

  （真回落时 `BULK_CONFIRM_REQUIRED` 自己会带 `"threshold": 9999`）⇒ **执行时以读数自报的值为准**。

★ **两条必须分清的事**（此前被混为一谈）：
1. `V-05` 的会话锁是 **per-worktree**（防"同一工作树两个 pytest 会话互删夹具"）——
   **它防不住"多条工作树合起来打穿同一份共享删除预算"**；

### V-10 **工具输出即证据：任何「零命中 / 零输出」结论必须附地板真值**

**为什么**（本会话实测，代价 = 主理人两轮错误广播 + 5 处报告写错根因 + 多人多次中招）：

本环境的裸 `grep` **不是** GNU grep：

```
$ command -v grep
…/WorkBuddy.app/Contents/Resources/app.asar.unpacked/cli/vendor/shim/brokered-bin/grep
$ grep --version
toybox 0.8.13 (is not GNU grep 9.0)
$ /usr/bin/grep --version
grep (BSD grep, GNU compatible) 2.6.0-FreeBSD      ← 这个**支持** GNU 扩展
```

toybox 的极简 `grep` **不支持 GNU 扩展运算符**，且失败形态是
**`0` 命中 + `rc=1` + 无任何诊断**。而 `rc=1` 正是 grep「真的没有匹配」的**合法退出码**
⇒ **「模式不被支持」与「确实零匹配」完全不可区分**（`G-62` 家族）。
⇒ 它**不是** `rc=0`（我先前的广播写错过这一点，属**二次编造观测值**）。

**失效集合（2026-09-16 双引擎实测 + Python `re` 地板真值；受控输入经 stdin，零文件写入）**：

| 语法 | 裸BRE | `/usr/bin/grep` BRE | 裸 `-E`（**原样**） | `/usr/bin/grep -E`（**原样**） | 处置 |
|---|---|---|---|---|---|
| `\|` 交替 | **0** rc1 ✗ | 8 ✓ | **0** rc1 ✗ | **0** rc1 ✗ | 改 `-E` **且去掉反斜杠**（`a\|b`→`a|b`），或多 `-e` |
| `\+` / `\?` | **0** rc1 ✗ | 5 / 7 ✓ | **0** rc1 ✗ | **0** rc1 ✗ | 同上（`\+`→`+`、`\?`→`?`） |
| `\<…\>` 词边界 / `\b` | **0** rc1 ✗ | 1 ✓ | **0** rc1 ✗ | 1 ✓ | ★ 改 **`-w`**（`-E` 救不了） |
| `\(…\)\1` 组 + 反向引用 | 1 ✓ | 1 ✓ | **0** rc1 ✗ | **rc2 + `invalid backreference number`** | ★ **留在 BRE**；`-E` 下**没有**此语法 |
| `\.` / 纯字面 / `^` `$` | 1 / 5 ✓ | 1 / 5 ✓ | 1 / 5 ✓ | 1 / 5 ✓ | 原样即可 |
| `ab\{2\}` 区间 | 1 ✓ | 1 ✓ | **0** rc1 ✗ | **0** rc1 ✗ | 改 `-E` **且写成 `{2}`** |

★★★ **"遇到问题就加个 `-E`"是危险建议 —— 这是被真值推翻的一格。**
`-E` 只对**已改写成 ERE 的模式**有效；若**原样字符串**加 `-E`，上表四类里**三类仍然 0 / rc1**，
等于**从一种静默换到另一种（更广的）静默**。
⇒ 正确动作 = **`-E` + 同时改写模式**（去反斜杠、`\|`→`|`、`\{n\}`→`{n}`）；
   词边界用 `-w`；**反向引用只能留在 BRE**。
★★ **且失败并非一律静默**：`/usr/bin/grep -E '\(abc\)\1'` 给 **`rc=2` + 诊断**（响亮）
—— 说明"`-E` 会静默丢反向引用"这条**也要按引擎分开说**，不能一句话盖全。
★★★ **机械加 `-E` 有两种坏形态，第二种更坏**（`auditor-batch11` 实测补正）：
- 输入里**没有**该字面时 → **静默零**（0 命中 + `rc=1`）；
- 输入里**有**该字面时 → **静默错配**（`-E 'a\{2\}b'` 去匹配**字面的** `a{2}b`，`rc=0` 有命中）。
⇒ **「匹配到了别的东西」比「零命中」更危险**：零命中至少让人起疑，
  错配**看起来像成功**，且**不会进任何 `rc` 判据**。
⇒ 故本节的纪律不是"看有没有输出"，而是 **"语义是否被改写必须有人看过"**。
★ 数字由 `system/scripts/ops/probe_grep_engine.sh` **现跑产出**（含 `od -c` 模式字节列）。
★★ **但本表初版有一处过度声称，现更正**（`ws-criterion-effectiveness` 指出，**它说得对**）：
上表 `-E` 两列**只有数字、没有属于它们自己的判定与真值** ——
"★真值"那一列属于 **BRE 意图**（`a\|z` 的意图真值 = 8），而 `-E` 列跑的是**原样字符串**；
**若仪器真去判这两列，两个引擎都会被误判成 MISMATCH**。
⇒ 因此「本表已按仪器订正」这句**只对 BRE 两列成立**：
`-E` 四格的结论来自**独立复现**（多人实测）而非本仪器的判定。
★★ 顺带两条仪器自身的缺陷（同一轮登记，**待修**）：
- **输入被写了两遍**（shell 的 `printf` 与 Python 的 `lines`）⇒ 改一处会**静默让全部判定失效**（`G-06` 同族）；
- 用来证明"模式字节到达 grep"的 `od`/`sed`/`head` **自己仍走 PATH** ——
  而本仪器的**全部前提**正是"PATH 首位不是真工具"（`V-10` 规矩 5 的自我适用）。
**本表初版有 4 格是错的**（来自更早的临时探测、无仪器背书）—— 这正是本规范自己那条
「无真值的格子不许进结论」被违反后的实测代价。

★★ **没有「一律改成 X」的安全写法**：`-E` 修好了 `\|`/`\+`/`\?`，却**弄坏了**反向引用与词边界。
★★ 本会话曾有两条**不安全建议**上了纸（"一律 `grep -E`"），按本表**作废**。
★★★ **反向反例同样要防：不许把「某些语法失效」过度概括成「裸 `grep` 一概不可信」。**
上表里**六类语法在裸 `grep` 下完全正常**（纯字面、`^` `$` 锚点、`\.`、`\{n,m\}`、`\(…\)\1` 分组反向引用）。
把它说成"工具整体不可信"会**误伤**大量正确用法，并逼人去做无谓的改写 —— 与 `G-27`（关键词式门禁把人逼向委婉语）同一机理。

**规矩**：
1. ★★ **没有「无方言」的工具** —— 三个引擎三种语义，**同一个 `\|` 给出三个不同答案**：

   | 引擎 | `\|` 的语义 | 实测 | 地板真值 | 判定 |
   |---|---|---|---|---|
   | 裸 `grep`（toybox 0.8.13） | **不认识** | 0 + rc1 | 20 | ✗ 静默零 |
   | `/usr/bin/grep`（BSD BRE） | **交替** | 20 | 20 | ✓ |
   | `rg` CLI（ripgrep 15.2.0） | **字面竖线** | 语法错 **rc=2（响亮）** | 20 | ✗ 但**响亮** |
   | `Grep` 工具（同一 ripgrep 内核，**经包装层**） | **字面竖线** | **0（静默）** | 20 | ✗ **静默零** |

   ⇒ ★ **"改用 `Grep` 工具"不是 `\|` 的解** —— 这条推荐语本人写过、**已按实测作废**。
   `Grep` 工具同样是**方言**而非方言中立：**支持** `\b`（实测 8 = 真值 ✓），
   但**不支持反向引用**。
   ★★★ **且 `rg` CLI 与 `Grep` 工具在「响亮性」上不是同一个对象**（`ws-step56-skipped` 实测）：
   - `rg -c '(.)\1' <f>` → **`rc=2` + `rg: regex parse error: …(?:(.)\1)`**（**响亮**，并提示 `--pcre2`）；
   - `Grep` 工具同模式 → **"No matches found"（静默 0）**。
   ⇒ **包装层把 `rg` 的响亮信号销毁了** —— 这是 `G-62` 最坏的一种形态：
     **上游愿意响亮，下游把它变成了静默**。
   ⇒ **故"改用 `rg` CLI" 优于 "改用 `Grep` 工具"。**
   ★★ **本节的「地板真值」一律引仪器，不引活体文件的一次性读数**
   （`ws-degrade-contract` 指出，且**它说得对：本规范此前违反了它自己的 `V-11` 仪器轴**）：
   - 仪器的真值建立在**冻结的 8 行受控输入**上（`probe_grep_engine.sh` 的 `print_content`，
     脚本里已明写"任何真值都只能相对它成立"）⇒ **天生不漂**，这是**刻意设计**；
   - 而"活体仓库文件上一次读数"**会漂**：同一模式 `(.)\1` 打在 `verify.py` 上，
     `98d0c32`（710 行）= **607** → `5318e74` = **615** → `main@603f2b5`（729 行）= **625**。
   ⇒ **不要把活体依赖搬进仪器**（给它加"被测对象指纹"是错的方向）。
   ⇒ 引用反向引用这一族时，**引仪器里已有的 `\(abc\)\1` / `(abc)\1` 两格**（无需活体文件）。
   ★ 上表那三个数**保留为"活体读数会漂"的实例**，但必须与**对象 + 版本 + 行数**同写。
   ★★ **跨引擎"同名参数不同义"**（本轮新形态）：`grep -E` = **基本→扩展正则**；
   `rg -E` = **`--encoding`**（实测 `rg -E '(abc)\1'` 报 `unknown encoding: (abc)\1`）。
   ⇒ 把一条 grep 命令迁到 rg 时，**同名参数会静默改意**。**迁移必须逐参数核对语义，不得凭名字。**
   **选工具的原则是"你知道它的方言"，不是"选个更高级的"。**
2. ★★★ **任何"零命中"结论的最小可判定形式 = 五元组**
   （`auditor-batch11` 提出，**比我原来的三元组更完整** —— 它补了缺的那两元）：

   ```
   ( 输入 + 模式 + 引擎 + rc + 地板真值 )
   ```

   ★ **"输入"必须写明**：同一模式在不同输入上的正确结果**不同** ——
   本会话 `-E 'a\{2\}b'` 的 `0`（输入里无字面 `a{2}b`）与别人测到的"错配命中"（输入里有）
   **不是矛盾，是两个输入**。缺"输入"这一元，两份正确读数会被读成互相打脸。
   ★ **"模式"必须写到字节**（`od -c`），否则分不清"grep 不支持"与"外壳吃掉了 `\`"。
   ★ `Grep` 工具**不暴露 `rc`** ⇒ 用它时必须额外给地板真值，否则连"零"和"出错"都分不开。
   **"零命中"结论缺任一元即为无效证据。**
   ★★ **第三类新形态（`auditor-batch11` 发现）：「碰巧正确的假证据」。**
   假零命中**恰好支持了一个方向正确的结论** ⇒ **下游会因为结论对而不再检查论据**。
   ⇒ 处置：**证据的有效性独立于结论的正确性**；结论对**不**豁免对其论据的复核。
   ★★★ **第四类（`ws-degrade-contract` 发现，比第三类更隐蔽）：「理由已换、结论未变」。**
   事例：某断言的**底层事实**已变（`output_refs` 这个字段**已有了生产写入点** `pipeline.py:415`），
   但**结论仍然成立** —— 因为它现在成立的**理由已经换成另一个**（仓库里根本没有 `status=done` 行，
   因为 `T-18`：step 7/8 永不注册 ⇒ `blocked` 恒真）。
   ⇒ 危险在于：**一旦新理由的前提翻转（`T-18` 落地、`done` 行出现），该结论立刻失效，而旧理由不会自己更新**。
   ⇒ 处置：**改"理由"，不只改"结论"**；并给该断言**标注它依赖的前提**。
   ★ 这与第三类同根：**结论对，掩盖了论据/理由已经坏了**。三类合起来是同一件事的不同切面 ——
     **"结论正确"从来不是"论证仍然有效"的证据。**
   ★★ **第三引擎也要列**：`Grep` 工具（ripgrep / Rust regex）自己的静默零来自
   **lookahead 等 Rust regex 不支持的语法**（`零命中(?!X)` → "No matches found" 而非报错）。
   ⇒ **三个引擎各有各的静默零** ⇒ **"换个工具"从来不是解药，唯一解是每格带地板真值。**
3. ★★ **地板真值（第三法）**：任何"零命中 / 全都是 0 / 一致"的对照表，**每一格都必须有独立真值列**
   （Python `re`、另一引擎、或被测程序自身的输出）。**无真值的格子不许进结论**
   —— 主理人本会话就曾把 `{3}` 那格"两边都是 0"读成"两引擎一致"，**那格不携带信息**；
   ★★ **且必须配「控制组」**（`ws-step56-skipped` 在第五轮补，**它是这一族能被反复漏掉的那一环**）：
   **一个已知非零的对照**（同一条命令打在一个**必然命中**的目标上）⇒ 证明**测量路径本身是活的**。
   缺它时，"全都是 0"既可能是"对象真的没有"，也可能是"**测量链路死了**" —— 两者不可区分（`G-62`）。
   ⇒ 合格形态 = **原文 + 真值 + 控制组**三件套，缺一不可。
   ★ 本轮这条被**五个角色从五个角度各纠了一轮**（规则本身 → `rc` → 引擎 → 层 → 控制组），
   每轮都发现上一轮没发现的东西 ⇒ **它是本轮迭代次数最多的一条**，请勿以为它已经收敛过一次就到底了；
4. ★★ **管道会吞掉退出码 —— 带 `| head` / `| wc` / `| tail` 的命令，`rc` 列一律不可用。**
   本会话「`rc=1` 还是 `exit 0`」的争论**已闭环**（`ws-verify-shard` 差分 + `ws-step56-skipped` 独立复算，
   同文件同模式，**唯一变量 = 是否过管道**）：

   | 形态 | 结果 |
   |---|---|
   | `grep …` 单独跑 | 0 行 **rc=1** |
   | `grep … \| head -1` | 0 行 **rc=0** ← ★ 管道吞码 |
   | `grep … \| wc -l` | 0 行 **rc=0** |
   | `grep … > /dev/null` | **rc=1** ← 重定向不吞码，**只有管道吞** |

   ★ 管道吞的是**所有非零码，不只 `1`**：错路径的 `rc=2`（No such file）过 `| head` 后**也变 `rc=0`**。
   ⇒ **两个读数都是真的，只是对象不同**（`rc=1` 是 grep 的，`exit 0` 是管道的）。
   正确写法：`{ cmd; echo "EXIT=$?"; } 2>&1 | tail -N`；
   zsh 的 `PIPESTATUS` 是 **1-based**，`${PIPESTATUS[0]:-$?}` 会**静默回落**到 `$?`；
5. ★★★ **取数命令本身，不得使用"尚未证明可用"的语法。**
   测量一个工具的方言时，**测量脚手架必须只用已证明正确的那条路径取数** ——
   否则就是**用坏仪器测坏仪器**。本会话的实测代价：同一问题出现
   **四轮互相矛盾的读数**，根因就是复核命令里带了 `\|`（作者本人也点出了这一点，却仍发布了读数）。
   ⇒ **规范仪器 = `system/scripts/ops/probe_grep_engine.sh`**：恒 `exit 0`（**仪器不是门禁**，
   只出数据不做判定），输出含 **引擎指纹 + 模式字节 `od -c` + 地板真值 + 逐格判定**。
   `od -c` 那一列是关键：**它把"grep 不支持"与"外壳吃掉了 `\`"分开**
   —— 缺这一列，读数为 0 时你无法知道是哪一个。
   **2026-09-16 实测（8 格全带真值）**：
   `\|` `\+` `\?` `\<…\>` 在**裸 `grep`** 下均为 **0 / rc1** ✗（`bare-BAD`）；
   `\{n\}` `\.` 纯字面 `\(…\)\1` 两引擎皆 ✓（`both-OK`）；
   ★ **`/usr/bin/grep` 8 格全对，无一处 `real-BAD`**
   ⇒ 「`/usr/bin/grep` 也会丢 `\|`」与「`\+`/`\?` 在裸 `grep` 下正常」**两条说法均已被本仪器证伪**。
6. ★★★ **地板真值的语义必须与「意图」对齐，且必须显式声明你在比「意图」还是比「串」**
   （`ws-degrade-contract` 提出，**它解释了本节表格出错 4 格的机理**）：
   - **问「这条模式在我的意图下该匹配多少」** ⇒ 地板真值必须由
     **按该引擎语法重写的同一意图**得出（`\|`→`|`、`\+`→`+`、`\{n\}`→`{n}`）。
     ★ **否则基准自己也是方言的产物**，你会拿一个方言去判另一个方言 —— 这正是
     "把原样串喂给 `-E`、再把 Python `re` 的读数当真值"时出错的原因。
   - **问「这个引擎对这个串做了什么」** ⇒ 必须用**同一个串**（这正是**揭示方言差异**的方法，
     也是本轮定位 toybox 失效集合的办法）。
   ⇒ 两种问法**都需要**，但**混用就是 `V-11` 仪器轴越界**。**必须在表头/脚注里写明是哪一种。**

**元规矩（比上面六行更重要）**：
> ★★★ **任何因果解释，在落纸或广播之前，必须先有一次「区分实验」。**
> 要求：**≥2 个候选机制**假设 + **单变量** + **反向对照**（"不该失效的用法必须仍然正常"）。
>
> **不做的后果，本会话已实测两轮**：给"零命中"**编故事**（"BSD `grep` BRE 不支持 `\|`" —— 现象对、
> 根因错：不是 BSD，是 toybox shim），**向全队广播**，再由下级的实测把我纠回来；
> 我在纠正时又**编了第二个观测值**（把 `rc` 写成 `0`）。
> ⇒ **"零输出"至少有三个候选因**：① 确实没有；② **模式语法不被支持**；③ 路径/参数写错。
> **没有区分实验就无法在 ① 与 ② 之间选择** —— 而 ② 恰恰是静默的。

### V-11 **「举证半径 = 结论半径」—— 结论的「主语」不得比实测样本更宽**

**为什么**（`ws-criterion-effectiveness` 综合本轮三条错提出；本条与 `V-10` **互补、不可互替**）：

本轮三条错误**形态完全相同**：结论的**主语比实测样本更宽**。

| 轴 | 越界形态 | 本会话实例 |
|---|---|---|

### V-12 **无人值守场景下，会调起编辑器的命令必须显式给非交互参数**

**为什么**（本会话实测事故）：在无 TTY 的环境里执行裸 `git merge main`：
git 报 `Merge with strategy ort failed`，紧接 `merge: Waiting for the editor to close`
⇒ **挂起** ⇒ 被外部终止 ⇒ 仓库里留下 `MERGE_HEAD` 与**编辑器模板污染过的** `MERGE_MSG`；
接着一次 `git commit --no-edit` 就把模板行**写进了提交信息**。事后靠
**先确认 `git diff --cached --stat` 为空**再做 `--amend` 才清理干净。

**规矩**：
1. 合并一律写 **`git merge --no-edit <ref>`**（不要依赖 `GIT_EDITOR` / `core.editor` 的默认值）；
2. 任何**可能调起编辑器 / 分页器 / 交互提示**的命令，在无人值守上下文里都要显式给非交互参数
   （`--no-edit` / `--no-pager` / `-m` / `--non-interactive`）；
3. ★ 事后清理**只许 `--amend` 提交信息**（先证明暂存区干净），**绝不 `rebase`/`reset` 已发布的主干**；
4. ★ 判据：`git rev-parse -q --verify MERGE_HEAD` 必须为空 ——
   **`MERGE_HEAD` 存在 = 上一轮合并没有结束**，此时任何提交都会写进别人的中间态（`G-61` 同族）。
   ★ **边界（`ws-degrade-contract` 补正）**：**快进（FF）合并不产生提交、不调起编辑器**，
   故 `--no-edit` 对 FF 是**无操作**、并非"安全"的来源。
   本条的适用范围是**非 FF / 会产生提交**的合并，以及所有**无人值守**的 git 操作；
   **不要把"写了 `--no-edit`"当成"这次合并安全"的证据** —— 那只证明参数写了。
5. ★★★ **提交信息一律 `git commit -F <文件>` —— 不要在 `-m` 里写反引号或 `$()`。**
   shell 会把 `-m "… `x` …"` 里的反引号当**命令替换**执行，并把那些词**从消息里吃掉**：
   ```
   (eval):1: command not found: degraded
   (eval):1: command not found: last_valid_result_ref
   ```
   ⇒ 消息里留下**语义空缺**（`⇒ 修法**必须** predicate ；`），**而屏幕上看仍读得通** ⇒ **逐字不可察觉**。
   ★★ **为什么这条比其他同类更重**：在本流程里**提交信息本身就是证据**
   （`V-11` 规矩 6 要求"读改动面/提交正文"来判断发生了什么）⇒ **被吞词 = 证据自己缺了一块**。
   ★ 同族先例：`pre-commit.sh` 里那句 `line 161: G-61: command not found` —— 同一个词被同一个机制吞掉。
   ★ 补救：若该提交**未被其他 ref 引用**，可用 `-F` **重写其信息**（`--amend`，先证暂存区干净）；
   **不得**为掩盖它去改文件内容，**不得** `--no-verify`。
6. ★★★ **派单／规格必须自足 —— 不得用「见上一封」「按前述」这类引用。**
   实测（`ws-degrade-contract`）：**连续两封带"（见上一封）"的派单它一封都没收到**，
   而"上一封"恰好是我**已撤回**的那封（内含被推翻的规格）⇒ 它手上**零可执行规格**。
   ⇒ 后果分两层：① 它**不敢动手**（正确 —— 猜错方向会把错误**换个方向**，那是 `G-42`/`G-43` 的复发形态）；
   ② 它**白等一轮**。
   ★ 根因是消息投递**既不保证按序、也不保证不丢**；而"引用"把**送达**当成了前提。
   ⇒ 纪律：**规格内联写全**（落点定义、行号+对象+SHA、接口选择、验收判据、反向对照），
   **每条派单独立可执行**；引用只能用于"补充阅读"，不能承载**必需**信息。
