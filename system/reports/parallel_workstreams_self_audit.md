## 二、过程自审：违规与缺口（**3 条，含 1 条严重**）

### ❌ 缺口 A（严重）：并行三流**没有经过 `§九` 独立审计**

`§九` 原文：**「实现方不得自证完成。」** 我在集成时做的是：
「核改动面（文件范围）+ 跑测试（11 批全绿）」。

**这不等于独立审计**：我没有**换人**去"先读验收标准、再读代码、逐条判 AC、做三项探测"。于是：

| 未做的 `§九` 动作 | 后果 |
|---|---|
| 三项探测（write-read-reload / 让缺失层响亮失败 / 接线体检） | **三流的 AC 判定全部来自作者自报**，我只验证了"测试通过" |
| 逐条 AC 判 PASS/FAIL/UNKNOWN | `ws/compute` 自报 **AC-03 PARTIAL**，我**未独立复核**该判定是否偏松 |
| 逐条对照 `施工图 §8` 12 条纪律找违例 | 未做 |

→ **正确表述：并行三流是"已合并（merged）"，不是"已验收（accepted）"。**
→ 这也**正是**批次 4 的教训所指向的：**我自己跑测试不能替代换人审计**（批次 4 的首轮审计就抓出了 5 条我漏掉的 FAIL）。

### ⚠️ 缺口 B：**跨 WS 直连**，未走主理人中转

`ws/claim` 报告原文：「`scripts/graph.forward_closure` 本工作区不存在（属 ws/graph），
**已发接口契约给 `ws-graph-engineer`**」。

**违反** `G-7`（沟通只用 SendMessage + 报告文件）与团队协议（**禁止成员互相直连，跨成员信息流须经主理人中转**）。
我在派单时**没有把这条写成"硬禁止 + 唯一替代通道"**，只写了"与主理人沟通只用 SendMessage"。
→ 风险：接口可能在两个 Agent 之间悄悄对齐，**主理人失去对接口的可见性**。
→ 处置：集成时我**独立核过** `forward_closure` 的签名确实与其调用一致（`graph.__all__` 含 `forward_closure`）；
但这是**事后补救**，不是过程控制。

## 四、结果自审：这批并行到底值不值

### 4.1 量化产出

| 项 | 数值 |
|---|---|
| 新增模块 | `scripts/compute/**`（13 文件）· `scripts/graph/**`（8 模块）· `scripts/validators/**` + `scripts/claim/**` |
| 新增测试 | **158 条**（compute 82 · graph 36 · validators 20 · claim 20） |
| 全量基线 | **231 → 389 passed**（11 批）· 20 项门禁全绿 |
| 耗时 | 三流**并行**，各 10~17 分钟；**串行则约 40 分钟** |
| 集成成本 | 3 次 merge 全干净 + 统一加批次 + 2 处对齐 = **很低**（解耦分析成立） |

### 4.2 ★ 最有价值的产出：暴露 **3 处真缺陷**，且**同属一类**

| 缺陷 | 暴露者 | 类别 |
|---|---|---|
| `freeze_guard` 对 `ast.Import` 取 `node.module`（属性不存在）→ **决策域内任何裸 `import` 都让守卫自己崩** | `ws/graph` | **"从没被真实输入跑过"** |
| `Claim.status="active"` **不在 `Ch6 §E` 五态内** → **真实链路写出的 claim 带违约状态** | `ws/claim` | 同类 |
| `class X(str, Enum)` 的 `str(member)` 返回 `'X.member'` → 状态机把**每次合法迁移**都误判 | `ws/claim`（**实测踩到**） | 同类 |

**规律（值得写进规范）**：**空包的"第一次真实输入"必然暴露缺陷**。
这三处都因为 `scripts/{decision,graph}/**` 与 `claims` 的真实写入路径**此前从未被驱动过**。
→ **推论**：本批 `ws/decision`（`scripts/decision/**` 从空包变成有内容）**极可能再暴露一批同类缺陷** ——
这正是它值得单独开一条流、并由独立审计盯住的理由。

### 4.3 三处缺陷都被**根治**而非绕过

① `getattr(node,"module",None)`；② `ClaimStatus` **封闭枚举** + 设计初始态；③ 基类改 **`enum.StrEnum`**（`str(member)==member.value`）。
★ 并登记：仓库另有 **~30 个 `(str, Enum)` 枚举**同一陷阱 → **待评估**（本批不动，避免范围失控）。

### 4.4 反向证据：**没有被误报掩盖**

| 检查 | 结果 |
|---|---|
| 是否"修了字面没修实质"？ | 三流 `--no-verify` 的红**不是代码问题**，我 bootstrap 后**钩子自然绿** → 证实 |
| 是否"测试退化成无判别力"？ | 我自造 7 条探针复核 `A-3` 四绕过**全 exit 1** + 反向对照**不误报**；并接受审计员的"B/C 两组不具备判别力"判断（已入档） |
| 是否"声明与事实不符"？ | 抓到 3 处（含我自己 1 处脆断言、1 处漏重建 schema）→ 均已修 |

## 五、结论与必须做的补救

### 5.1 结论（**不给"看起来对"的结论**）

| 项 | 判定 |
|---|---|
| git 纪律 | ✅ **零违规**（reflog 硬证据） |
| 解耦划分 | ✅ 成立（零冲突，与预判一致） |
| 产出与验证 | ✅ 158 新测试、389 全绿、20 门禁绿 |
| **验收状态** | ❌ **未验收** —— 只"已合并"；`§九` 独立审计**未做** |
| 我的复核强度 | ⚠️ 够查范围与测试，**不够替代独立审计** |

### 5.2 立即补救项

1. **`§九` 独立审计**（换人、新会话、对抗性）审 `ws/compute` · `ws/graph` · `ws/claim` 三流 ——
   基准 = 三流各自的 `ws_*_dod.md` + 对应设计节；要求做**三项探测**与**逐条 AC 四态判定**；
   **特别复核 `ws/compute` 自报的 AC-03 PARTIAL 是否偏松**。
2. `§八 N-1` 对三流补**手动走查**（compute 真算一次、graph 真传播一次、claim 真迁移一次），存原始输出。
3. `§八 N-5` 三流 `converge` 审计 → 产出 gap 清单 → 入 `phase1_gap_register.md`。
