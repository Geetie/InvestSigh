## R-02 · base64 / 同形字是否主动解码归一（回应 DoD `Q-02`）

**裁决：不主动「解码后执行」、不主动「归一化后判定」；只保证「解码/归一化后仍作数据」。**

- 设计原文（`Ch9 §3.4.6` 措施 1）只要求「外部文本只进 `raw/` 与 `claims`」，
  **未规定**需要主动解码或归一化。
- 主动解码会**引入新的解析面与误报面**：与 DoD `AC-33`（禁见词就杀）直接冲突。
- 因此本批次取**更保守的一面**：**不做额外解码**——「不做」＝不新增，符合
  `§5.3`「需要引入设计里没有的东西 → 停」的反面（不引入即无需上报）。
- **允许**（不禁止）执行器对可疑编码**记 `note` 观测**，但**不得据此 fail**
  （否则即落入「见词就杀」）。

**类别：设计未规定，取保守面＝不新增。**

## R-04 · `scripts/guard/` 与 `scripts/ingest/guard.py` 是否同一模块（回应 DoD `Q-04`）

**裁决：不是同一模块，不合并。本批次只做 `scripts/guard/`。**

| 模块 | 职责 | 设计锚点 | 归属 |
|---|---|---|---|
| `scripts/guard/` | **注入防护**：外部文本不得成为指令（数据/指令分离、角色标注、工具白名单效果） | `Ch9 §2.4.1` / `§3.4.6` / `§3.2.1`；`Ch6 §0` 复用声明行：「注入防护（`scripts/guard/`）……**全部沿用第九章**」 | **第九章既有权属** |
| `scripts/ingest/guard.py` | **采集来源访问白名单**（`access_restriction`）——「受限来源不越权采集」「每条 claim 可回溯公开入口」 | `Ch6 §I.1 N6.1-01`（+ `§N6.1-10` `rules/compliance.yaml`） | **第六章新增（采集层）** |

**依据（两处原文对照，非冲突而是分工）**：
- `Ch6 §0` 把 `scripts/guard/` 列进**「复用声明」**清单 —— 即它是第九章的既有件，第六章**不重写**；
- `Ch6 §I.1 N6.1-01` 把 `scripts/ingest/guard.py` 写进**「第六章真正的新增」**语境下的需求行
  （其判据是"来源可回溯",属采集合规，与"文本不得成为指令"是两回事）。

**结论**：二者**不合并**（合并会把"注入防护"与"采集合规"两个不同判据搅在一起，
违反 `施工图 §8` 纪律 8「同名不同域必须消歧」）。本批次只交付 `scripts/guard/`；
`scripts/ingest/guard.py` 随**阶段② 采集层**（依赖 `registry/sources.yaml:access_restriction`）交付。

**类别：设计已写死（两处原文对照后即可定），非冲突。**

## R-06 · 给工程师的硬提示（本批次最容易做反的地方）

1. **`AC-33` 是本批次的核心，不是附加项**：判据必须是**效果**（改没改规则内核 / 触没触发工具 /
   绕没绕过建议链），**不得**依赖「关键词黑名单」。一个只会对注入词报错的守卫会**通过所有正向用例**，
   却在真实研究文本上（"某分析师建议买入 NVDA"）天天误报 —— 按 `施工图 §八 N-2`
   「降噪就是有效性」，误报刷屏的终点是**门禁被关掉**，比不设防更糟。
2. **不得留孤儿模块**：执行器与守卫必须真的被调用/被门禁跑（`§一 底线 2` 真接线）。
3. **不得让新守卫拖慢门禁**：AST 扫描单遍、配置读取走 `_common._cached_yaml()`、
   带全局副作用的加载器必须 `try/finally` 收尾（上一批次 D-19~D-23 的教训）。
4. **不得把「无被检对象」当「已验证」**：空 `raw/` / 空 `claims` 必须显式记 `note`（`AC-34`）。
5. **docstring 不得声称代码没做的事**（上一轮审计 `D-15` 的教训）。

## R-07 · 收口点不得是"仅供测试调用"的变相孤儿（回应设计 §2.3/§2.4 与 §9 U-06）

**背景**：架构设计把 `rulewrite.write_rule()` 与 `toolwatch.request_tool()` 定为**收口点**
（chokepoint）。但若**只有测试**调用它们，它们就是 `§一 底线 2` 说的第 2 类假交付
（Wiring Failure：**能通过 100% 覆盖率的测试**，但主流程从不触发）。
架构 §9 `U-06` 已诚实登记"本批次无系统侧调用方" —— 但"没有调用方"与"不可被调用"是两件事，
**不能以"将来会有"结案**。

**裁决：两个收口点必须各有一个非测试的生产入口，否则视为孤儿。**

具体做法（**不新增防护维度，只把设计自己的断言变成可验证的**）：

- `scripts/guard/executor.py` **必须**提供路由入口：

```python
def handle_external_request(
    root: str | Path,
    *,
    kind: str,                 # "rule_write" | "tool_call" | "data"
    payload: Mapping[str, Any],
    ledger: ToolCallLedger,
) -> IngestResult:
    """外部来源的**请求**入口：按调用方声明的 kind 路由。

    - kind="rule_write" → `rulewrite.write_rule(...)`（→ 恒抛 ReadOnlyRuleViolation）
                          → 捕获后返回 `status="blocked"` + note（**不吞异常语义**：blocked 即明确降级）
    - kind="tool_call"  → `toolwatch.request_tool(origin=ORIGIN_EXTERNAL, ...)`（→ 恒抛）
                          → 捕获后返回 `status="blocked"` + note
    - kind="data"       → 走 `process_external_text` 的**数据**路径（正常吸收）
    - 未知 kind         → `status="blocked"` + note（**明确拒绝，不静默当数据**）
    """
```

- **关键：`kind` 由调用方声明，不是对文本做词面分类。**
  因此**不违反** `AC-33`（禁关键词黑名单）与 `R-02`（不主动解码/归一化）——
  它表达的是"**系统试图做 X**"这一事实，而不是"文本里出现了 Y 词"。
- **收益**：`write_rule` / `request_tool` 从"仅测试可达"变为"**有生产入口可达**"，
  `§一 底线 2` 的孤儿风险关闭；且守卫可新增一条可执行断言：
  **两个收口点必须在 `executor.py` 的函数体内被调用**（AST 绑定，与 R-01/D 同一手法）。

**类别：把设计自己的断言（"收口点存在且外部来源必拒"）落成可验证形态 —— 非新增防护维度。**
